### 2. AI 审核 fail-closed（P0 安全）

**涉及文件**：config.py、AiReviewService.java、reviewer.py

## 五、后续演进项

> 以下为非审查报告内、修复过程中识别出的架构演进建议，不影响当前主流程，按规模上升后逐步推进。

### 1. 异步任务独立线程池（中优先级）

**现状**：`PostServiceImpl` 所有异步调用（`runAsync` / `supplyAsync` 共 5 处：AI 审核 3 处 + Feign 并行查询 2 处）未传 executor，默认走 `ForkJoinPool.commonPool()`。

**隐患**：
- **全局共享**：JVM 内所有 CompletableFuture 默认任务挤同一池，post 服务内部各异步点互相影响
- **快慢任务混跑**：AI 审核（HTTP 调用，秒级慢任务）与 batchGetUsers / batchGetSectionNames（毫秒级快任务）混在同一池，慢任务占满 worker 时拖累快任务
- **无界队列 + 无拒绝策略**：commonPool 用工作窃取，任务堆积无显式上限，极端情况可能 OOM
- **无监控**：commonPool 不暴露指标，排队/拒绝情况不可观测
- **线程命名不可读**：`ForkJoinPool-1-worker-3` 无法区分业务，日志排查困难

**演进方案**：按任务类型拆分独立线程池

```java
@Configuration
public class ThreadPoolConfig {

    /** 快任务：Feign 批量查询（高并发、毫秒级） */
    @Bean("queryExecutor")
    public ExecutorService queryExecutor() {
        return new ThreadPoolExecutor(
            8, 16, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(500),
            new ThreadFactoryBuilder().setNameFormat("query-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }

    /** 慢任务：AI 审核（低并发、秒级） */
    @Bean("aiReviewExecutor")
    public ExecutorService aiReviewExecutor() {
        return new ThreadPoolExecutor(
            2, 4, 120, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(100),
            new ThreadFactoryBuilder().setNameFormat("ai-review-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }
}

// 使用：显式传 executor
CompletableFuture.supplyAsync(() -> feignClient.xxx(), queryExecutor);
CompletableFuture.runAsync(() -> aiReviewService.review(...), aiReviewExecutor);
```

**收益**：快慢任务隔离、有界防 OOM、命名可观测、可独立加监控指标。

**触发时机**：AI 审核并发上升、或异步点扩展到 10+ 处时落地。当前规模（5 处异步）下用 commonPool 可接受。

**涉及文件（演进时改动）**：新增 ThreadPoolConfig.java、PostServiceImpl.java 5 处异步调用补 executor 参数。
**配套演进**：与下方"TransmittableThreadLocal 替换手动 wrap"一起落地，新建线程池时 `ContextSnapshotExecutor.wrap(raw)` 一行同时处理 TTL 装饰 + 原生 ThreadLocal 捕获。

### 2. TransmittableThreadLocal 替换手动 wrap（中优先级）

**现状**：`RequestContextHolder` 底层是 JDK 原生 `ThreadLocal`（`NamedThreadLocal`），异步线程读不到主线程的请求头，当前用 `RequestContextUtil.wrap()` 在每个异步点手动传递上下文。

**隐患**：
- 异步调用点持续增多后极易漏写 wrap，遗漏一处即导致 Feign 请求头缺失
- 手动传递仅覆盖 `RequestAttributes`，链路追踪 TraceId、MDC 日志上下文等其他 ThreadLocal 无法同步携带

**演进方案**：引入阿里 [transmittable-thread-local](https://github.com/alibaba/transmittable-thread-local)（TTL），在线程池层面统一处理上下文透传，替代分散在业务代码中的 `wrap()` 调用。

> 核心机制：TTL 不依赖"新建线程"时机（`InheritableThreadLocal` 仅在线程首次创建时拷贝一次，线程池复用线程时直接失效），而是**每次提交任务时捕获主线程上下文快照**，任务执行前回填到 worker 线程，执行结束后 `finally` 恢复 worker 线程原有值——彻底避免线程池复用串味。

**关键约束（必须理解）**：

`TtlExecutors.getTtlExecutorService()` 只能自动透传 `TransmittableThreadLocal`，**Spring 内部的 `RequestContextHolder`（`NamedThreadLocal`）和 SLF4J 的 MDC 是 JDK 原生 ThreadLocal，不会被自动传递**。需要在提交任务时额外捕获这些原生 ThreadLocal 的值，再在 worker 线程手动回填。

也就是说，从"手动 wrap"升级到 TTL 不是一行装饰就完事，要补齐两样东西：
1. **线程池装饰**：`TtlExecutors.getTtlExecutorService()` —— 管自定义 TransmittableThreadLocal
2. **上下文捕获器**：在任务提交时统一捕获 `RequestAttributes` / MDC —— 管 Spring 原生 ThreadLocal

```xml
<!-- common 公共模块引入依赖 -->
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>transmittable-thread-local</artifactId>
    <version>2.14.5</version>
</dependency>
```

```java
/**
 * 上下文透传线程池装饰器
 * 在 TTL 线程池基础上，统一捕获 RequestAttributes 和 MDC，worker 线程执行时回填
 */
public class ContextSnapshotExecutor {

    public static ExecutorService wrap(ThreadPoolExecutor raw) {
        return TtlExecutors.getTtlExecutorService(raw, task -> {
            // 主线程（提交任务时）捕获快照
            RequestAttributes attrs = RequestContextHolder.getRequestAttributes();
            Map<String, String> mdcCtx = MDC.getCopyOfContextMap();
            return () -> {
                // worker 线程执行前回填
                if (attrs != null) RequestContextHolder.setRequestAttributes(attrs);
                if (mdcCtx != null) MDC.setContextMap(mdcCtx);
                try {
                    task.run();
                } finally {
                    // 任务结束恢复 worker 线程原值，防止串请求
                    RequestContextHolder.resetRequestAttributes();
                    MDC.clear();
                }
            };
        });
    }
}

// 线程池配置：一处装饰，全局生效
@Bean("queryExecutor")
public ExecutorService queryExecutor() {
    ThreadPoolExecutor raw = new ThreadPoolExecutor(
        8, 16, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(500),
        new ThreadFactoryBuilder().setNameFormat("query-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy()
    );
    return ContextSnapshotExecutor.wrap(raw);
}
```

**改造前后对比**：

```java
// 改造前：每个异步点手动 wrap，易遗漏
CompletableFuture.supplyAsync(RequestContextUtil.wrap(() -> feignClient.xxx()), queryExecutor);

// 改造后：线程池已内建透传，业务代码零侵入
CompletableFuture.supplyAsync(() -> feignClient.xxx(), queryExecutor);
```

**编码强制规范**（防 commonPool 漏网）：
- 所有异步任务必须传入 TTL 包装后的自定义线程池
- **禁止**使用无参 `CompletableFuture.supplyAsync()`（默认走 `ForkJoinPool.commonPool()`，该池未被 TTL 包装，上下文照样丢失）
- CI 可配静态检查规则拦截无参调用

**与手动 wrap 的对比**：

| 维度 | 当前 wrap() | TTL 统一方案 |
|---|---|---|
| 依赖 | 零依赖 | 引入 TTL jar |
| 代码改动点 | 每个异步点手动一行 wrap | 线程池配置层一处改造，业务代码无感 |
| 可靠性 | 靠开发自觉，遗漏即 Bug | 统一拦截，不存在漏传递场景 |
| 传递范围 | 仅 RequestAttributes | RequestAttributes + MDC + 自定义 TTL 全覆盖 |
| 串请求防护 | 手动 finally 恢复 | TTL 框架级 finally 兜底，异常场景也安全 |

**备选路线**：Java Agent 模式（启动加 `-javaagent:ttl-agent.jar`），全局线程池自动增强，配合 `ttl.agent.enhance.framework.threadlocal` 系统属性，连 Spring 原生 ThreadLocal 也能一起透传。但 Agent 增启动复杂度、容器环境调试成本高，中小规模项目不建议，当前保留为知识储备。

**落地触发时机**：异步调用点扩展至 10+ 处，或出现遗忘 wrap 引发线上故障时推进。与上方"独立线程池"配套执行。

**涉及文件**：common/pom.xml（引依赖）、新增 ContextSnapshotExecutor.java（上下文捕获）、ThreadPoolConfig.java（池装饰）、PostServiceImpl.java（删除所有 wrap 调用）。
