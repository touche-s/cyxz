## 二、Critical 级别

### C1. RestTemplate 无超时配置 + 默认 ForkJoinPool 跑阻塞 HTTP（雪崩根因）

- **维度**：③资源与性能 + ④代码质量
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/config/PostConfig.java:11-13`
- **问题代码**：
  ```java
  @Bean
  public RestTemplate restTemplate() {
      return new RestTemplate();
  }
  ```
- **关联调用**：`AiReviewService.doPost` (L92) `restTemplate.postForEntity(...)`；调用方 `PostCommandService.java:98,185,395` 用 `CompletableFuture.runAsync(...)` 派发
- **风险描述**：`new RestTemplate()` 默认 `SimpleClientHttpRequestFactory`，connect/read timeout 均为 -1（无限）。AI 审核是秒级 HTTP 慢调用，若 Python AI 服务 TCP 挂起或响应慢，调用线程会被永久阻塞。该调用又跑在 `ForkJoinPool.commonPool()`（见 H1），一旦 AI 服务异常，commonPool 线程被耗尽，会连带拖垮 `PostQueryService.fillPostVOList` 的快任务并行查询（读路径热链路），导致整个 post 服务读/写异步链路雪崩。`handleReviewFailure` 的 catch 仅能捕获异常，无法处理"线程被永久挂起"场景。

## 三、High 级别

### H1. 全项目零自定义线程池，所有 CompletableFuture 走 ForkJoinPool.commonPool

- **维度**：③资源与性能
- **文件**：
  - `cyxz-post/src/main/java/com/cyxz/post/service/impl/PostCommandService.java:98,185,395`（AI 审核，秒级慢 HTTP）
  - `cyxz-post/src/main/java/com/cyxz/post/service/impl/PostQueryService.java:303,305,307,309,311`（Feign + DB，毫秒级快任务）
- **验证**：全代码库 grep `ThreadPoolExecutor|ExecutorService|ThreadPoolTaskExecutor` 零命中（业务模块），无 `@Bean Executor`/`@Async`/`@EnableAsync`
- **风险描述**：快慢任务混跑同一 commonPool：AI 审核（秒级 HTTP）与 batchGetUsers/getLikedPostIds（毫秒级）共享同一池；commonPool 工作窃取 + 无界队列无拒绝策略，极端情况 OOM 且无监控；线程名 `ForkJoinPool-1-worker-3` 不可观测。慢任务占满 worker 时直接拖累读路径的 fillPostVOList 并行查询。

### H2. 全项目无 Feign 超时配置，跨服务调用无 SLA 保障

- **维度**：④代码质量
- **文件**：全部 `application.yml`（post / comment / circle / auth / message / user）
- **验证**：全局搜索 `connectTimeout|readTimeout|connect-timeout|read-timeout` 零匹配
- **风险描述**：所有 Feign 客户端均未配置连接和读取超时。Spring Cloud OpenFeign 默认 HTTP 客户端在不显式配置时使用 JDK HttpURLConnection，readTimeout 默认为无限。`CommentServiceImpl.createComment()` 中连续发起 3 次 Feign 调用，任一下游服务卡住都会导致评论接口无限期挂起。`PostQueryService.fillPostVOList()` 中 5 个 `CompletableFuture` 也各自包含 Feign 调用，无超时则 `allOf().join()` 可能永久阻塞。

### H3. 权限缓存删除在 @Transactional 内部，先删缓存后提交 → 缓存-DB 不一致

- **维度**：③资源与性能
- **文件**：
  - `cyxz-circle/src/main/java/com/cyxz/circle/service/impl/CircleServiceImpl.java:107`（joinCircle）、`125`（leaveCircle）、`323`（appointAdmin）、`338`（removeAdmin）、`364`（kickMember）
  - `cyxz-auth/src/main/java/com/cyxz/auth/service/RoleAdminService.java:95`（updateRolePermissions）、`147`（assignUserGlobalRole）
- **问题代码**（CircleServiceImpl.java:94-108）：
  ```java
  @Transactional(rollbackFor = Exception.class)
  public void joinCircle(Long userId, Long circleId) {
      ...
      circleRoleAssignmentMapper.assignRole(...);  // DB 写（未提交）
      invalidateCirclePermissionCache(userId, circleId);  // Redis delete（立即生效）
  }
  ```
- **风险描述**：`stringRedisTemplate.delete` 不受 DB 事务管理，在事务提交前就执行。竞态场景：T1 删缓存 → T2 读缓存未命中 → T2 读 DB（T1 未提交，读到旧权限）→ T2 写回缓存（旧值）→ T1 提交 → 缓存残留旧权限直到 TTL 过期。权限缓存错误直接导致越权或权限丢失。与项目硬约束"MQ 必须在 afterCommit"同理，缓存删除也应放到 afterCommit。

### H4. hardDeletePost 在 @Transactional 内发 ES 同步 MQ，违反 afterCommit 约束

- **维度**：③资源与性能
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/service/impl/PostCommandService.java:275-303`
- **问题代码**：
  ```java
  @Transactional(rollbackFor = Exception.class)
  public void hardDeletePost(Long userId, Long postId) {
      ...
      postMapper.deleteById(postId);              // L300 DB 删（未提交）
      postQueryService.evictDetailCache(postId);  // L301 Redis 删
      postEsSyncService.syncPostToEsDelete(postId);  // L303 发 MQ "DELETE"
      // L307 才注册 afterCommit 处理 Feign 评论清理
  }
  ```
- **风险描述**：`syncPostToEsDelete` 在事务提交前就发 MQ（RabbitTemplate 默认不参与 DB 事务）。若事务提交失败回滚，DB 帖子仍在但 ES 文档已被消费端删除，DB-ES 永久不一致（无后续补偿事件）。项目硬约束明文要求"MQ 通知必须在 afterCommit 回调发送"，此处违反。同一方法的 Feign 调用已正确放到 afterCommit（L307-319），但 ES 同步 MQ 漏改。

- **问题代码**：
  ```java
  public PageResult<FollowUserVO> listFollowers(Long userId, int page, int size) {

      ...
      List<FollowUserVO> records = followMapper.selectFollowersPage(userId, offset, size);
  ```

### H6. UserAdminService.disable/enable 缺少站主保护校验（权限提升）

- **维度**：②安全与权限
- **文件**：`cyxz-auth/src/main/java/com/cyxz/auth/service/UserAdminService.java:57-65, 72-81`
- **问题代码**：
  ```java
  public void disable(Long id) {
      SysUserPO user = sysUserMapper.selectById(id);
      if (user == null) {
          throw new BusinessException(ErrorCode.NOT_FOUND, "用户不存在");
      }
      user.setStatus(0);
      sysUserMapper.updateById(user);
  }
  ```
- **风险描述**：Controller 层 `@PreAuthorize("hasAuthority('user:manage:disable')")` 允许 PLATFORM_ADMIN 调用。但 Service 层未校验目标用户是否为 SITE_OWNER，导致 PLATFORM_ADMIN 可以禁用站主账号。与设计文档 `docs/功能设计/权限体系设计.md` 第 3.6.3 节明确要求矛盾——"平台管理员不能禁用/操作站主"。`enable` 方法存在同样问题。这是权限提升漏洞：PLATFORM_ADMIN 可通过禁用站主账号实现权限接管。

### H7. RoleAdminService.assignUserGlobalRole 可将 SITE_OWNER 角色分配给任意用户（权限提升）

- **维度**：②安全与权限
- **文件**：`cyxz-auth/src/main/java/com/cyxz/auth/service/RoleAdminService.java:126-149`
- **风险描述**：Controller 层 `@PreAuthorize("hasAuthority('role:manage:assign')")` 允许 PLATFORM_ADMIN 调用。Service 层仅校验了 `role.getScope() == "GLOBAL"`，但未校验目标角色是否为 `SITE_OWNER`（built_in=1, code=SITE_OWNER）。PLATFORM_ADMIN 可以将 SITE_OWNER 角色分配给自己或任何用户，实现从平台管理员到站主的权限提升。也可将 SITE_OWNER 降级为 USER，等效于剥夺站主权限。

### H8. RoleAdminService.updateRolePermissions 可修改任意角色权限含内置角色（权限提升）

- **维度**：②安全与权限
- **文件**：`cyxz-auth/src/main/java/com/cyxz/auth/service/RoleAdminService.java:73-96`
- **风险描述**：Service 层未校验 `role.getBuiltIn() == 1`，允许修改任何角色的权限分配，包括 SITE_OWNER（role_id=1, built_in=1）。PLATFORM_ADMIN 可以：(1) 清空 SITE_OWNER 角色的所有权限，使站主失去全部管理能力；(2) 给 USER 角色添加所有权限，使每个普通用户获得管理员权限。设计文档第 3.6.2 节要求"内置角色（built_in=1）禁止删除和改 code"，但代码连权限修改都未拦截。

### H9. GlobalExceptionHandler 缺少常见异常类型处理，统一返回 500

- **维度**：④代码质量
- **文件**：`cyxz-common/src/main/java/com/cyxz/common/handler/GlobalExceptionHandler.java:54-58`
- **问题代码**：仅处理 `BusinessException`、`BindException`、`Exception` 三类，其余全部走兜底 500
- **风险描述**：以下常见异常会落入兜底 `handleException(Exception e)` 返回 `500001 系统异常`，而非语义正确的 400/413：
  - `MaxUploadSizeExceededException`（上传文件超限）→ 应返回 413/400「文件过大」
  - `HttpMessageNotReadableException`（JSON 格式错误/缺少 body）→ 应返回 400
  - `MethodArgumentTypeMismatchException`（路径变量类型不匹配，如 `/post/abc`）→ 应返回 400
  - `NoHandlerFoundException`（路径不存在）→ 应返回 404
  - `ConstraintViolationException`（`@RequestParam` 校验失败）→ 应返回 400
  前端无法区分「客户端错误」与「服务端故障」，且 500 错误会触发不必要的告警。

### H10. PostEsSyncService 吞掉 MQ 发送异常，ES 与 DB 静默不一致

- **维度**：④代码质量
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/service/impl/PostEsSyncService.java:27-34, 36-46`
- **问题代码**：
  ```java
  public void syncPostToEs(PostPO po) {
      try {
          // ... rabbitTemplate.convertAndSend(...)
      } catch (Exception e) {
          log.error("ES 同步消息发送失败: postId={}", po.getId(), e);
      }

  ```
- **风险描述**：MQ 消息发送失败时仅 `log.error` 后吞掉异常，不抛出、不重试、无补偿。虽然消费端有 DLQ 保障，但**生产端发送失败的消息根本不会进入 MQ**，DLQ 也收不到。帖子状态在 DB 已变更（如 APPROVED→DELETED），但 ES 索引仍为旧状态，搜索结果会展示已删除帖子，且无任何机制发现和修复不一致。`PostCommandService` 中 6 处调用 `syncPostToEs`/`syncPostToEsDelete` 均受影响。

### H11. CommentServiceImpl 576 行，Command/Query 职责混合

- **维度**：④代码质量
- **文件**：`cyxz-comment/src/main/java/com/cyxz/comment/service/impl/CommentServiceImpl.java`（全文件 576 行）
- **风险描述**：post 模块已按 CQRS 拆分为 `PostCommandService` / `PostQueryService` / `PostReviewService` / `PostStatsService`，但 comment 模块未同步重构。`CommentServiceImpl` 同时承担：评论创建（含 3 次 Feign 调用 + 编程式事务 + MQ 通知）、评论删除（级联软删 + Redis 计数）、5 种列表查询（各自含不同的 VO 填充逻辑）。类内还有 7 个私有辅助方法。读写混在一个类中导致：事务边界模糊（`createComment` 用 `TransactionTemplate`、`deleteComment` 用 `@Transactional`）、缓存策略难以统一、修改写逻辑时可能误读逻辑。

### H12. FollowServiceImpl 分页参数未校验 — offset 可为负数或超大值

- **维度**：①空指针与边界
- **文件**：`cyxz-user/src/main/java/com/cyxz/user/service/impl/FollowServiceImpl.java:156, 178`
- **问题代码**：
  ```java
  int offset = (page - 1) * size;  // ← 未调 PageConstants.pageOf()，page/size 原样使用
  ```
- **风险描述**：Controller 仅设 `@RequestParam(defaultValue=...)`，default 只在参数缺失时生效，无法阻止前端显式传 `page=0`、`page=-1`、`size=999999`。当 `page=0` 时 offset=-20，MySQL 抛 `1064` 语法错误返回 500；当 `size=999999` 时无上限保护，可一次拉取海量数据拖垮 DB。`(page-1)*size` 在 page 和 size 均为大值时存在 Integer 溢出风险。

### H13. PostStatsService.getReceivedLikes 分页参数未校验

## 四、Medium 级别

### M1. 登出/改密用 KEYS 通配清理圈子权限缓存

- **维度**：③资源与性能
- **文件**：`cyxz-auth/src/main/java/com/cyxz/auth/service/impl/AuthServiceImpl.java:278-287`
- **风险描述**：`KEYS auth:circle:{userId}:*` 是 O(N) 阻塞命令，扫描整个 Redis keyspace，单线程 Redis 在扫描期间无法处理其他请求。生产环境 key 数量大时会引发 Redis 延迟尖刺。应改用 `SCAN` 迭代删除。

### M2. 计数刷库 HGETALL 全量加载 + 无界循环

- **维度**：③资源与性能
- **文件**：`cyxz-common/src/main/java/com/cyxz/common/service/AbstractCountFlushService.java:36-66`
- **风险描述**：`post:like:delta`/`post:view:delta` 等 Hash 在热门场景可能积累数万 field（30 秒窗口内被互动的帖子）。HGETALL 一次性全量拉进 JVM 内存；循环内逐条 DB UPDATE 串行执行，无分批无事务边界。刷库耗时 > 30s 时下次任务积压。应改用 HSCAN 分批 + 批量 UPDATE。

### M3. 帖子详情缓存不缓存 null → 缓存穿透

- **维度**：③资源与性能
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/service/impl/PostQueryService.java:69-84`
- **风险描述**：不存在的 postId 每次请求都打到 DB。攻击者构造大量不存在的 postId 可打穿缓存直接压 DB。`RedisConfig` 也配了 `disableCachingNullValues()`，即便手动塞 null 也不行。应缓存短 TTL 的空标记（如 60s）或用布隆过滤器前置拦截。

### M4. 评论分页每次翻页触发全量 COUNT

- **维度**：③资源与性能
- **文件**：`cyxz-comment/src/main/java/com/cyxz/comment/service/impl/CommentServiceImpl.java:211-258`
- **风险描述**：`listComments` 每次翻页都对 `comment` 表做一次全量 COUNT（顶级+子回复）。热门帖子评论上千条时，InnoDB COUNT 需扫描索引全部匹配行，每页请求都付出这个代价。已有 Redis `post:comment:delta` 增量数据，可维护一个 `post:comment_count:{postId}` 缓存避免每次 COUNT。

### M5. 私信会话查询用 OR 条件，索引无法合并

- **维度**：③资源与性能
- **文件**：`cyxz-message/src/main/java/com/cyxz/message/service/impl/ChatServiceImpl.java:51-55, 176-189`
- **风险描述**：生成 `WHERE user_id_1 = ? OR user_id_2 = ?`，MySQL 无法用 `idx_user1_time`/`idx_user2_time` 做索引合并，只能走其中一个索引 + 回表过滤另一半。《数据库索引设计.md》第 117-139 行明文要求"代码层拆成两条 UNION 查询，分别走 idx_user1_time 和 idx_user2_time"，但实际代码未实现。`unreadTotal` 同样用 OR 且把全部会话拉进内存求和（应下推到 SQL `SUM(CASE WHEN ...)`）。

### M6. 关注/粉丝/收到的点赞均用 LIMIT offset 深度分页

- **维度**：③资源与性能
- **文件**：
  - `cyxz-user/src/main/java/com/cyxz/user/mapper/UserFollowMapper.java:73, 91`
  - `cyxz-post/src/main/java/com/cyxz/post/mapper/PostLikeMapper.java:54`
- **风险描述**：`LIMIT 9990, 10` 仍需扫描前 10000 行才返回。大 V 粉丝深翻页时延迟显著上升。`PostLikeMapper.selectReceivedLikes` 还额外 INNER JOIN post 表，深分页代价更高。应改游标分页（`WHERE create_time < last_cursor ORDER BY create_time DESC LIMIT size`）。

### M7. Dashboard 串行 4 次 DB 查询 + Feign

- **维度**：③资源与性能
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/service/impl/PostStatsService.java:85-107`
- **风险描述**：4 次 DB 往返 + Feign 串行执行，数据中心接口总延迟 = 各查询耗时之和。这 4 个查询相互无依赖，完全可以用 `CompletableFuture.supplyAsync` 并行（注意需用自定义线程池，避免加重 H1）。

### M8. recordView 每次浏览都 selectById 打 DB

- **维度**：③资源与性能
- **文件**：`cyxz-post/src/main/java/com/cyxz/post/service/impl/PostInteractionServiceImpl.java:141-158`
- **风险描述**：热门帖子 1000 浏览/秒 → 1000 次 selectById/秒。`PostQueryService.getById` 已缓存 PostVO（含 status），recordView 可直接读缓存判定状态，无需 DB。当前实现完全绕过缓存。

### M9. CircleCountFlushServiceImpl 全量加载圈子

### 第一优先级（功能性 + 安全漏洞）

| 编号 | 问题 | 理由 |
|------|------|------|
| C1 + H1 | RestTemplate 无超时 + commonPool 雪崩 | 雪崩根因，AI 服务异常会拖垮整个 post 服务 |

## 七、已确认良好的方面（排除假阳性）

以下领域经检查**不存在**所述类别的问题：

- **IDOR 越权**：PostCommandService 的 update/delete/hardDelete/pin/unpin 均校验 `po.getUserId().equals(userId)`；CommentServiceImpl.deleteComment 校验评论作者或帖子作者；ChatServiceImpl 校验会话成员身份；NotificationServiceImpl.markRead 的 SQL 带 `receiverId = userId` 条件；UploadController.deleteFile 校验文件路径中的 userId 归属
- **内部接口外部访问**：Gateway `JwtAuthFilter` 通过 `path.contains("/internal/")` 阻断所有外部对 internal 接口的访问
- **JWT 安全**：密钥通过 `${JWT_SECRET}` 环境变量注入，无硬编码；Token 含 exp 过期时间；refresh token 调用 `blacklistToken` 拉黑旧 Token
- **SQL 注入**：全项目无 MyBatis `${}` 拼接；`PostQueryService` 的 `wrapper.last()` 中 `field` 经 `ALLOWED_SORT_FIELDS` 白名单校验
- **XSS**：前端 Vue 文件中无 `v-html` 使用；文章帖子通过 `<v-md-preview>` 渲染，markdown-it 默认 `html: false` 转义原始 HTML
- **VO 字段泄漏**：`UserAdminVO`/`UserProfileVO` 均不含 password/salt/deleted 等敏感字段
- **权限注解遗漏**：所有管理类写操作均有 `@PreAuthorize`；SpEL 表达式全部使用 `hasAuthority`
- **Feign Result 解包**：所有显式 `.getData()` 调用点均有前置 `isSuccess()` + `data == null` 判断
- **N+1 查询（读路径）**：`PostQueryService.fillPostVOList` 用 `CompletableFuture` 并行批量查；`CommentServiceImpl` 用 `countRepliesByParents` + `batchGetPostInfo` 批量查
- **CQRS 拆分**：`PostServiceImpl` 已成功拆分为 5 个子 Service
- **分页封装统一**：全项目无散落的 `new Page()`
- **Redis Key 集中管理**：`CacheKeyConstants` 集中管理，有 `getXxxKey()` 辅助方法
- **敏感配置**：所有 `application.yml` 敏感配置（DB 密码、JWT secret、MinIO key）均通过 `${ENV_VAR}` 注入
- **Feign 降级工厂统一**：统一继承 `AbstractFeignFallbackFactory`
- **无 Entity 直接作为返回值**：所有 Service 均有 `toVO` / `convertToVO` 转换
