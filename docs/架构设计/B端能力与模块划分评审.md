### 1.2 内容审核能力：B 端核心亮点

```
草稿 → 待审核 → AI 审核 → 通过 / 拒绝 → 人工复审兜底
```

已实现：

- AI 自动审核（文本 + 图片）
- AI 异常转人工待审（fail-closed 策略，不直接放行）
- 后台待审核列表
- 人工审核通过 / 拒绝
- 审核结果通知（MQ 异步）
- 审核通过后增量同步 ES
- 审核通过 / 删除后事件驱动更新圈子帖子数

面试表述建议：

> 我没有把 AI 审核当成最终裁决，而是把它设计成内容审核状态机的一环。AI 调用异常或结果不确定时，帖子保持 `PENDING`，交由人工后台处理，从而避免"AI 异常直接放行"或"AI 异常误删内容"。

### 1.3 举报治理：从"审核后台"升级为"治理后台"

`cyxz-governance` 作为独立治理中心，只记录治理决策与编排处置，不拥有帖子、评论等业务实体的数据写权限：

```
用户提交举报
  → governance 保存举报记录
  → 管理员审核
  → 发布 ContentTakedownEvent
  → post/comment 各自消费并执行处置
```

前端 `ReportManagement.vue` 已实现：状态筛选、类型筛选、原因搜索、分页、通过/驳回、强制处理意见。

**当前缺口（影响业务闭环质量）：**

1. **举报详情缺少被举报内容上下文/快照**：管理员需要自行跳转查询原内容。最小实现：举报详情接口通过 Feign 只读查询帖子/评论摘要，不复制业务数据到 governance 数据库。
2. **处置动作粒度不足**：当前仅支持下架。后续可扩展为 `DELETE` / `HIDE` / `WARN` / `NO_ACTION`，扩展 `ContentTakedownEvent` 的处置字段即可，不新增服务。

### 1.4 审计与统计：已具备 B 端"工程感"

`cyxz-audit` 与 `cyxz-analytics` 均已有后端、前端入口和事件模型，不再是"规划中"。

**数据看板（AnalyticsDashboard.vue 已实现）：**

- 新增用户、新增帖子、审核量、新建圈子、新增入圈、处理举报
- 7/14/30 天趋势图（ECharts 折线图）
- 多指标切换

架构上，这属于合理的 CQRS 使用场景：

```
业务服务发生写操作
  → 发送 AnalyticsEvent
  → analytics 消费并聚合日统计
  → B 端只查询 analytics 本地读模型
```

避免管理后台首页为六个统计卡片分别 Feign 调用六个业务服务。

**审计日志：**

```
管理员执行敏感操作
  → 业务服务发布 AuditEvent
  → audit 消费并写入审计日志
  → 后台按条件检索
```

价值不在于"多建一个服务"，而在于避免每个业务服务重复建 `operation_log` 表、重复实现审计查询和保留策略。

## 二、模块划分评审

### 2.1 总体结论

目前模块划分**合理偏细，但仍在可控范围**。不建议合并 `governance`、`audit`、`analytics`，也不建议当前新增 `admin-bff`、`ops-config`、`chat`、`notify`。

面试表述建议：

> 服务不是按页面拆分，而是按数据归属和写模型拆分。帖子、评论、圈子等服务各自拥有事实数据；跨服务查询使用 Feign；跨服务写操作通过 RabbitMQ 事件解耦，接受短暂最终一致性。

### 2.2 cyxz-auth：认证与平台级 RBAC

职责：注册、登录、登出、JWT 签发、用户启用/禁用、角色管理、权限管理、用户与角色关系。

**边界原则：**

- `cyxz-user` 维护个人资料、关注关系
- `cyxz-auth` 维护账户、登录和角色
- 不要让 `cyxz-user` 反过来直接操作角色权限表

此为当前正确边界，应保持。

### 2.3 cyxz-post 与 cyxz-comment：应继续分开

虽然帖子和评论关系紧密，但保持独立是合理的：

- 帖子有状态机、审核、ES 同步、收藏、点赞、计数
- 评论有树形回复、评论点赞、内容处置
- 两者均可被举报，但通过治理事件松耦合
- 未来评论量增大时，分页、楼中楼、热点缓存策略与帖子完全不同

不建议合并。

### 2.4 cyxz-circle：圈子、板块、成员、申请都留在一起

建圈申请和入圈申请已迁入 circle，属正确调整。原因是审批结果直接影响圈子领域内的实体：

```
建圈申请通过 → 创建 Circle → 指定 owner → 初始化 section
入圈申请通过 → 建立 CircleMember → 更新成员计数 → 刷新权限缓存
```

上述流程均可通过**同一服务、本地事务**保证一致性，无需 governance 编排多个同步写。

### 2.5 cyxz-governance：职责收敛为"治理编排"

**治理服务应拥有：**

- report 举报记录
- 审核结论
- 处置决定
- 处置事件发布
- 治理待办查询

**不应拥有：**

- post / comment / circle 表
- 用户资料表
- 直接跨库更新内容状态

未来"封禁用户、禁言、内容申诉、风控命中记录"可继续留在 `cyxz-governance`，都属于平台治理决策。但不建议做成无边界的"运营中心服务"。

### 2.6 cyxz-audit 与 cyxz-analytics：拆分成立

| 服务 | 写入数据 | 核心目的 | 查询特点 |
|---|---|---|---|
| `cyxz-audit` | 操作明细 | 追责、合规、问题排查 | 按操作人、时间、对象检索 |
| `cyxz-analytics` | 聚合指标 | 运营看板、趋势分析 | 按日期、指标聚合 |

不建议合并。数据生命周期、访问模式、索引方式、保留策略完全不同。

### 2.7 各领域归属总结表

| 业务场景 | 归属模块 | 原因 |
|---|---|---|
| 用户举报帖子/评论 | `cyxz-governance` | 跨内容域的治理决策与处置编排 |
| 建圈申请 | `cyxz-circle` | 审批结果直接创建圈子，本地事务保证 |
| 入圈申请 | `cyxz-circle` | 审批结果直接创建成员关系，本地事务保证 |
| 用户注册申请 | 当前无需实现 | 当前开放注册，不形成独立领域 |
| 敏感词/审核策略 | 暂留 `cyxz-post` | 当前体量不值得单独服务 |
| 管理员操作记录 | `cyxz-audit` | 跨域只读审计模型 |
| 运营数据聚合 | `cyxz-analytics` | 跨域统计读模型 |
| 内容处置（禁言/封禁） | `cyxz-governance` | 平台治理决策，不直接跨库写业务表 |
