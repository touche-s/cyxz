# 次元小站 MySQL 索引设计文档

> 9 个独立数据库 | 24 张业务表 | 58 个索引
> 2026-08-09 更新：post 表 3 个复合索引已落地（见 db/init.sql 与 db/migrations/20260809_post_indexes.sql）

---

## 一、post 表（帖子核心表）-- 数据量最大

**当前索引（2026-08-09 已落地）：**

| 索引 | 字段 | 类型 | 说明 |
|---|---|---|---|
| PRIMARY | id | 主键 | — |
| idx_user_status_time | (user_id, status, create_time) | 联合 | 首页/个人页帖子列表，覆盖 WHERE + ORDER BY |
| idx_circle_status_time | (circle_id, status, create_time) | 联合 | 圈子帖子列表，覆盖 WHERE + ORDER BY |
| idx_user_pinned | (user_id, status, is_pinned, pinned_time) | 联合 | 用户置顶帖查询 |
| idx_section_id | section_id | 单列 | 按板块筛选（独立查询场景） |

> 原单列索引 idx_user_id / idx_circle_id / idx_status / idx_create_time 已删除，
> 它们的查询场景被上方 3 个复合索引最左前缀覆盖，冗余索引会拖慢写入。

**高频查询命中分析：**

```sql
-- 首页帖子列表：按用户 + 状态 + 时间排序
WHERE user_id = ? AND status = 2 ORDER BY create_time DESC
-- 命中 idx_user_status_time 全部三列（等值+等值+排序），Using index，无需回表 filesort
```

```sql
-- 圈子帖子列表
WHERE circle_id = ? AND status = 2 ORDER BY create_time DESC
-- 命中 idx_circle_status_time 全部三列，Using index
```

```sql
-- 置顶帖子
WHERE user_id = ? AND status = 2 AND is_pinned = 1 ORDER BY pinned_time DESC
-- 命中 idx_user_pinned 全部四列，is_pinned 区分度低（0/1）放中间列
```

## 二、sys_user_role（用户-角色关联表）-- RBAC 核心表

**索引：**

| 索引 | 字段 | 类型 |
|---|---|---|
| PRIMARY | (user_id, role_id, circle_id) | 复合主键 |
| idx_user_tenant | (user_id, circle_id) | 联合索引 |

**登录鉴权查询（最左前缀命中）：**

```sql
-- 查用户全局角色
SELECT r.code FROM sys_user_role ur
JOIN sys_role r ON ur.role_id = r.id
WHERE ur.user_id = ? AND ur.circle_id = 0
-- 命中 idx_user_tenant 最左两列 (user_id, circle_id)，覆盖完整 WHERE 条件
```

**圈子权限查询（覆盖索引）：**

```sql
-- 查用户在某个圈子的角色
SELECT role_id FROM sys_user_role
WHERE user_id = ? AND circle_id = ?
-- 命中复合主键全部列，且 SELECT 的 role_id 就在索引里，覆盖索引
```

**为什么 user_id 放最左？** 因为所有查询都带 user_id（查"某个用户的角色"），符合最左前缀原则。如果反过来 circle_id 放最左，查全局角色（circle_id=0）的场景依然可用，但语义上先按用户过滤更合理。

## 三、notification（通知表）-- 索引设计最佳范例

**索引：**

| 索引 | 字段 | 类型 |
|---|---|---|
| PRIMARY | id | 主键 |
| uk_dedup | (receiver_id, sender_id, type, target_id) | 唯一索引（去重） |
| idx_receiver_read | (receiver_id, is_read, create_time) | 联合索引 |
| idx_receiver_type | (receiver_id, type, create_time) | 联合索引 |

**未读通知列表（完美覆盖）：**

```sql
SELECT * FROM notification
WHERE receiver_id = ? AND is_read = 0
ORDER BY create_time DESC
-- 命中 idx_receiver_read 全部三列，等值 + 等值 + 排序，Extra: Using index
-- receiver_id 最左列 → is_read 中间等值列 → create_time 排序列，顺序正确
```

**按类型筛选通知：**

```sql
WHERE receiver_id = ? AND type = ? ORDER BY create_time DESC
-- 命中 idx_receiver_type，同样是等值 + 等值 + 排序
```

**去重唯一索引：**

```sql
-- 同一发送者对同一接收者的同一类型同一目标，不重复通知
INSERT IGNORE INTO notification (receiver_id, sender_id, type, target_id, ...)
-- uk_dedup 自动拦截重复插入
```

**设计要点：** receiver_id 放在所有索引的最左列，因为通知永远按"收件人"维度查询。中间列 is_read/type 做等值过滤，最后一列 create_time 做排序。

## 四、conversation（私信会话表）-- 避免重复会话

**索引：**

| 索引 | 字段 | 类型 |
|---|---|---|
| PRIMARY | id | 主键 |
| uk_users | (user_id_1, user_id_2) | 唯一索引 |
| idx_user1_time | (user_id_1, last_message_at) | 联合索引 |
| idx_user2_time | (user_id_2, last_message_at) | 联合索引 |

**用户对去重约定：** 始终保证 `user_id_1 < user_id_2`。这样 A 和 B 的会话只会存一条，不会产生 `(A, B)` 和 `(B, A)` 两条记录。

**会话列表查询：**

```sql
-- 当前用户可以在这两列中的任何一列
SELECT * FROM conversation
WHERE user_id_1 = ? OR user_id_2 = ?
ORDER BY last_message_at DESC
-- OR 条件会导致索引失效（无法合并两个索引范围扫描）
-- 实际解决：代码层拆成两条 UNION 查询，分别走 idx_user1_time 和 idx_user2_time
```

## 五、user_follow（关注关系表）-- 关注/粉丝双向查询

**索引：**

| 索引 | 字段 | 类型 |
|---|---|---|
| PRIMARY | id | 主键 |
| uk_user_follow | (user_id, follow_user_id) | 唯一索引 |
| idx_user_id | user_id | 单列 |
| idx_follow_user_id | follow_user_id | 单列 |

**为什么是三个索引而不是一个联合索引？**

```sql
-- 查询某人关注了谁 → 走 idx_user_id
SELECT * FROM user_follow WHERE user_id = ? AND status = 1

-- 查询某人的粉丝（被谁关注）→ 走 idx_follow_user_id
SELECT * FROM user_follow WHERE follow_user_id = ? AND status = 1

-- 防止重复关注 → uk_user_follow
INSERT INTO user_follow (user_id, follow_user_id, status)
VALUES (?, ?, 1)
ON DUPLICATE KEY UPDATE status = 1
```

两个查询方向完全不同，联合索引 `(user_id, follow_user_id)` 只能覆盖"关注"方向的查询，"粉丝"方向查 `follow_user_id = ?` 跳过了最左列 user_id 会索引失效。所以必须为 follow_user_id 单独建索引。

## 六、关键设计原则总结

1. **最左前缀** — 联合索引列顺序 = WHERE 条件出现顺序，等值在前，范围/排序在后
2. **覆盖索引** — 高频查询的 SELECT 列尽量纳入索引，避免回表（权限查询、通知列表都是）
3. **区分度高的放前面** — status（4-5 个值）放最后，user_id（雪花 ID 高区分度）放最左
4. **唯一索引去重** — 点赞/关注/收藏用 `ON DUPLICATE KEY UPDATE`，比先查再改少一次查询
5. **单列 vs 联合** — OR 条件多方向查询时（关注/粉丝），拆成单独索引而不是一个联合索引
