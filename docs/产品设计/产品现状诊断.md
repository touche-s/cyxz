# 产品现状诊断

> 基于 2026-08-17 代码核对与前端路由盘点，功能清单以[功能全景图](../功能设计/功能全景图.md)为准。
> 本文档回答三个问题：产品现在做到了什么程度、断点在哪、接下来先改什么。规划与路线图见[产品设计](./产品设计.md)，不在此重复。

---

## 总体判断

**产品骨架的完整度显著高于运营就绪度。** 以圈子为组织单元的内容社区核心闭环——注册、发布、三层审核、互动、通知、搜索、治理——在 C 端 18 条路由与 B 端 11 个管理模块中全部跑通，后端治理链（举报 → 处置 → 三端联动）达到可演示的完整形态。差距集中在两处：增长侧缺少任何让新用户留下来、让老用户回来的机制；垂直化侧，"二次元社区"的语义兑现目前主要靠 UI 风格与命名，产品结构上与一个通用图文社区的差异还不大。

一句话：**这个产品已经"能跑"，但还不"能活"。**

## 用户旅程诊断

| 旅程 | 完整度 | 关键断点 | 影响人群 |
|---|---|---|---|
| 内容消费 | 高 | 无新用户引导，首页对陌生人不友好 | 全部新用户 |
| 内容创作 | 高 | 无系列/追更机制，创作者缺少回来的理由 | L3/L4 用户 |
| 社交互动 | 中 | 私信门槛高，无拉黑能力 | 活跃用户 |
| 治理参与 | 高 | 举报后无进度可查 | 举报人 |

### 内容消费旅程

注册 → 逛广场 → 进圈子 → 看帖 → 互动，这条路径上每个环节的功能都存在，但第一次访问的体验是断的。新用户注册完成后直接落入通用首页，没有任何选择兴趣圈子的引导环节——而产品设计文档把"我的圈子动态"定位为首页核心，这意味着产品最重要的设计在用户第一次使用时恰好缺席。对二次元用户而言，"我想看原神的内容"是真实需求，但当前发现路径只能是手动逛广场再逐个进圈子，发现成本高。

搜索是另一个收窄的入口：目前仅支持帖子全文检索，搜圈子、搜用户、搜标签均无。搜索是带着明确意图的用户（往往是最活跃的那批）最依赖的路径，单一维度等于把这类用户拒之门外。产品设计文档 2.7 已把统一搜索列入规划，从旅程视角看它的优先级应高于多数氛围类功能。

### 内容创作旅程

创作链路是四条旅程中最强的：发帖（敏感词预检可自检）→ AI 审核 → 上架/拒绝（附原因通知）→ 创作中心看数据（浏览/点赞/收藏/评论、月度趋势、Top 作品、收到的赞）。从发布到反馈的闭环完整，创作中心的颗粒度在同类学生项目中不常见。

断点在"回来"这个动作上。一个画师发了三张同人图、收获五十个赞之后，没有任何机制让他持续产出：没有创作系列让读者追更，没有更新通知推给关注者，没有活动帖给他命题。产品设计文档 3.5 的分层自评（L3 仅数据面板、L4 待实现）是准确的——当前创作中心是"报表"而非"激励"。对社区而言，让 1% 的创作者保持产出比给 99% 的读者加浏览功能重要得多，这是后续投入方向上最值得倾斜的一条线。

### 社交旅程

关注 → 动态流 → 互动 → 私信，主干存在。两个断点：

其一，私信以互相关注为前置。这个设计对spam 是有效防御，也符合"先建立弱关系再私聊"的社区调性，但对正常用户同样构成摩擦——想说"约稿可以吗"的读者必须先等到画师回关。更平衡的做法是保持门槛但补单向可达渠道（如评论区置顶联系方式、或允许向已关注对象发首条消息并需对方同意后续）。

其二，**没有拉黑**。全站检索不到任何屏蔽用户的能力，私信、评论、动态流均无法屏蔽特定用户。对一个以女性向、CP 讨论为主要场景的社区，"看到不想看到的人"几乎是必然发生的事，举报解决的是违规，拉黑解决的是日常不适——后者使用频率远高于前者，目前完全缺失。这是体验短板清单里最应该优先补的一项。

### 治理旅程

治理是后端做得最重的部分，前端也齐：C 端帖子/文章/评论三处举报入口、B 端举报工单处置、处置结果联动下架与通知、审计留痕、两级审批。作为学生项目，这条链的完整度超出预期。

断点在举报人的感知侧：提交举报后没有"我的举报"进度页（后端 `/report/mine` 接口已存在，前端未接）。举报是用户在替平台做义务劳动，没有任何反馈回路的义务劳动很难有第二次。补一个进度列表的成本很低，接口都是现成的。

> **2026-08-17 已落地**：用户中心新增「举报与申请」页（`UserCenterApplications.vue`），已接入我的举报（`/report/mine`）、我的建圈申请（`/circle-application/mine`）、我的入圈申请（`/circle-join-application/mine`），含状态徽章与处理备注展示。

## 垂直化兑现度

产品设计文档 3.4 自评了三条差距，本次核对全部属实，且可以更具体：

- **缺作品/IP 维度**属实。内容结构只有圈子+板块两层，"原神圈 - 同人创作板"里的帖子与"芙宁娜"没有结构化关联。垂直社区与通用社区的真正分界就在这里：用户心智里的导航单位是角色和作品，不是板块。
- **圈子归属感薄**属实。产品设计文档 2.3 说得直接——"当前圈子只是帖子筛选页"。圈友数、圈内公告、本周话题、活跃榜、自定义圈友称呼，这些制造归属的机制一项都未实现。圈子作为产品核心组织单元，目前的实际体验更接近一个筛选条件。
- **二次元语境停留在命名层**。"次元街"、"圈友"等词汇已进入 UI，但同担、追更、本圈热议这些承载社区文化的语义结构没有对应功能支撑。语境是功能的皮肤，当前只有皮肤。

需要说明：这些差距产品文档均已识别并排入 Phase 2/3，属于"已知未做"，不是"未知盲区"。诊断结论是方向判断没有问题，但**作品/IP 标签的优先级值得从 P1 提到 Phase 2 的最前面**——它是其他一切垂直化功能（IP 页、追更、同担）的地基，且不依赖任何运营资源，纯产品与工程投入。

## 冷启动与运营就绪度

这是最需要诚实面对的部分。全部社区功能在零真实用户下建成，没有任何数据能回答"用户会不会来、来了会不会发帖"这两个社区产品的生死问题。当前状态更接近一个功能验证平台，而非待上线产品。

三个运营就绪度缺口：

1. **种子内容策略缺失**。空社区的第一批帖子从哪来没有答案。常见路径是管理团队自产 50-100 篇示范内容覆盖头部圈子，这件事不需要写代码，但没有计划。
2. **邀请与准入机制缺失**。产品设计 Phase 1 列了"邀请 50-100 种子用户"，但产品内没有邀请码或任何准入控制，注册完全开放。冷启动期开放注册会把稀薄的流量摊薄在空房间里。
3. **无任何数据埋点**。产品决策依赖的漏斗数据（注册转化、首帖率、次周留存）没有采集方案，analytics 服务目前只接住了平台运营指标。

这三条不影响秋招展示，但影响这个产品"从项目变成产品"的可能性。如果后续真想推内测，它们是全部前置条件。

## 改进优先级

不另立路线图，仅对产品设计 Phase 1/2 的既有排序提出诊断性调整：

**应提前的三项**

1. 拉黑能力（社交安全网，纯工程，无依赖）
2. 举报进度页（后端就绪，前端半天工作量）
3. 作品/IP 标签（垂直化的地基，从 Phase 2 P1 提为最先做）

**可以后移的两项**

1. 圈子分层运营（S/A/B 级）——没有真实圈子规模前，分层规则无从校验
2. 商业化全部条目——依赖创作者生态，当前阶段设计价值大于实现价值

**维持不变的**：新用户引导、创作系列/追更、统一搜索，与产品文档判断一致，且都直接对应旅程断点。
