## 二、当前缓存现状：逐接口分析

### 2.1 帖子详情（GET /api/post/{postId}）— 已有缓存

[PostQueryService.getById()](file:///d:/Trae%20CN/cyxz/cyxz-post/src/main/java/com/cyxz/post/service/impl/PostQueryService.java#L87-L132) 实现了 Cache-Aside 模式：

```java
// 第 89-97 行：读缓存
String cacheKey = CacheKeyConstants.getPostDetailKey(postId);
PostVO cached = (PostVO) redisTemplate.opsForValue().get(cacheKey);
if (cached != null) {
    // 缓存命中后仅补填 liked/collected 状态（2 次 DB 查询）
    ...
    return cached;
}
// 第 99-125 行：缓存未命中，查 DB + Feign 并行填充 + 写缓存
...
redisTemplate.opsForValue().set(cacheKey, vo, Duration.ofMinutes(30));
```

**实际开销分析：**

| 场景 | DB 查询 | Feign 调用 | Redis |
|---|---|---|---|
| 缓存命中 | 2（like 状态 + collect 状态） | 0 | 1 GET |
| 缓存未命中 | 3（post + like + collect） | 3（user + circle + section） | 1 GET + 1 SET |

缓存命中时省了 1 次 DB + 3 次 Feign，但 `liked/collected` 状态仍需 2 次 DB 查询——因为这是跟当前用户绑定的，不能缓存。

### 2.2 帖子列表（GET /api/post/list）— 无缓存

[PostQueryService.listPosts()](file:///d:/Trae%20CN/cyxz/cyxz-post/src/main/java/com/cyxz/post/service/impl/PostQueryService.java#L137-L163) 每次请求全链路走 DB：

```java
// 第 157 行：查帖子分页（1 次 DB）
Page<PostPO> result = postMapper.selectPage(pageParam, wrapper);
// 第 159 行：并行填充 VO
List<PostVO> vos = fillPostVOList(result.getRecords(), currentUserId);
```

`fillPostVOList()`（第 312-342 行）通过 `postQueryExecutor`（core=8）并行执行 5 个任务：

| 任务 | 类型 | 占用资源 |
|---|---|---|
| `batchGetUsers` | Feign → user 服务 | 业务线程池 |
| `extractCircleNameMap` | Feign → circle 服务 | 业务线程池 |
| `extractSectionNameMap` | Feign → circle 服务 | 业务线程池 |
| `getLikedPostIds` | DB（post_like 表） | HikariCP |
| `getCollectedPostIds` | DB（post_collect 表） | HikariCP |

**单次列表请求的 DB 连接峰值：** 1（主查询）+ 2（并行 like/collect）= **3 个 HikariCP 连接**。8 个 postQueryExecutor 线程全部活跃时 = 24 个潜在并发 DB 连接需求，而默认 `maxPoolSize=10`。

### 2.3 点赞 / 收藏（写操作）— 每次多余一次 selectById

[PostInteractionServiceImpl.likePost()](file:///d:/Trae%20CN/cyxz/cyxz-post/src/main/java/com/cyxz/post/service/impl/PostInteractionServiceImpl.java#L59-L73)：

```java
// 第 59 行：先查帖子是否存在——白白多一次 DB 查询
PostPO po = postMapper.selectById(postId);
if (po == null || !isInteractable(po)) {
    throw new BusinessException(ErrorCode.POST_NOT_FOUND);

// 第 64 行：执行 upsert
```

1000 并发下写操作共 517 次（123+130+127+137），每次多 1 个 DB 查询 = 517 次无效查询。

## 三、瓶颈定位（基于代码实锤）

压测报告已定位到 HikariCP 连接池，下面从代码层面给出根因链：

```text
1000 并发
  ↓
Tomcat maxThreads=200（默认），acceptCount=100（默认）
  ↓ 200 个线程同时处理请求
  ↓
postQueryExecutor（core=8/queue=500）启动 8 个并行查询线程
  ↓
列表请求 × 42% = 约 84 个请求同时需要 3 个 DB 连接
写请求 × 32% = 约 64 个请求同时需要 2 个 DB 连接
详情请求 × 25% = 约 50 个请求同时需要 2 个 DB 连接
  ↓
峰值需求 ≈ 84×3 + 64×2 + 50×2 = 480 个连接
  ↓
HikariCP maxPoolSize=10（默认，代码未配置）
  ↓
连接池耗尽 → 排队 → connection-timeout 超时 → 报错
```

MySQL 默认 `max_connections=151`（docker-compose.yml 未配置），14 个服务 × 10 = 140，只剩 11 个余量。

## 四、优化方案

### 优化 1：帖子列表加 Redis 缓存（ROI 最高）

**改哪里：** `PostQueryService.listPosts()` 第 137 行之前插入缓存逻辑

**方案：** 缓存无用户状态的"干净"列表，命中后仅补填 `liked/collected`

```java
// 入口加缓存读
String cacheKey = CacheKeyConstants.getPostListKey(sectionId, circleId, sortBy, page, size);
@SuppressWarnings("unchecked")
PageResult<PostVO> cached = (PageResult<PostVO>) redisTemplate.opsForValue().get(cacheKey);
if (cached != null) {
    if (currentUserId != null) {
        fillInteractionStatus(cached, currentUserId);  // 仅 2 次 DB
    }
    return cached;
}

// ... 原有查库逻辑 ...

// 写缓存：存干净副本，liked/collected=false
List<PostVO> cleanRecords = vos.stream().peek(vo -> {
    vo.setLiked(false);
    vo.setCollected(false);
}).collect(Collectors.toList());
PageResult<PostVO> clean = PageResult.of(cleanRecords, total, page, size);
redisTemplate.opsForValue().set(cacheKey, clean, Duration.ofSeconds(30));
return result;
```

**TTL 为什么是 30 秒而非 30 分钟：** 首页列表是动态数据，新帖发布后最多 30 秒即可出现在列表。配合写操作主动清缓存。

**预期新开销：**

| 场景 | 原 DB 查询 | 优化后 DB 查询 | 节省 |
|---|---|---|---|
| 列表缓存命中 | 3 | 2（like+collect） | 33% |
| 列表缓存未命中 | 3 | 3（无变化）+ 1 次 Redis SET | — |

1000 并发下预计缓存命中率 > 90%，列表接口 DB 负载降低约 30%。

### 优化 2：HikariCP + MySQL 连接数调优

**改哪里：** 各服务 `application.yml` + `docker-compose.yml`

**各服务分级配置：**

```yaml
# cyxz-post / cyxz-gateway / cyxz-search（高流量，调整为 20）
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 3000

# 其余服务（auth/circle/comment/user/governance/audit/analytics/message/upload，保持 10）
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      connection-timeout: 3000
```

**MySQL 侧：**

```yaml
# docker-compose.yml 的 mysql 服务
mysql:
  image: mysql:8.0
  command: --max-connections=300
```

总计：3×20 + 11×10 = 170 连接，MySQL 300 上限足够。

### 优化 3：postQueryExecutor 拒绝策略改为 CallerRunsPolicy

**改哪里：** `PostConfig.java` 第 65 行

```java
// 当前
new ThreadPoolExecutor.AbortPolicy()
// 改为
new ThreadPoolExecutor.CallerRunsPolicy()
```

**理由：** `AbortPolicy` 在线程池满时直接抛 `RejectedExecutionException`，用户看到 500，重试又正常——体验极差。`CallerRunsPolicy` 让提交线程自己执行任务，相当于自动降级，响应变慢但不报错。

### 优化 4：点赞/收藏去除冗余 selectById

**改哪里：** `PostInteractionServiceImpl` 四组 like/unlike/collect/uncollect

**当前逻辑（每个操作）：**

```java
PostPO po = postMapper.selectById(postId);  // 多余查询
if (po == null || !isInteractable(po)) { throw ...; }
int rows = xxxMapper.upsertXxx(...);
```

**改为 SQL 层面校验：**

```xml
<insert id="upsertLike">
    INSERT INTO post_like (post_id, user_id, status, create_time, update_time)
    SELECT #{postId}, #{userId}, 1, NOW(), NOW()
    FROM post WHERE id = #{postId} AND status = 1   <!-- 校验存在于 SQL 内 -->
    ON DUPLICATE KEY UPDATE status = 1, update_time = NOW()
</insert>
```

`rows=0` 时说明帖子不存在或非已发布，返回错误。

**收益：** 四个写方法各少 1 次 DB 查询，1000 并发下约省 517 次查询。

### 优化 5：Redis Lettuce 连接池配置

**改哪里：** 各服务 `application.yml`

```yaml
spring:
  data:
    redis:
      lettuce:
        pool:
          max-active: 20
          max-idle: 10
          min-idle: 5
          max-wait: 3000ms
```

当前无任何 pool 配置，Lettuce 用默认单共享连接。`@PreventRepeat` 每次请求调 Redis Lua，1000 并发下单连接会成为瓶颈。
