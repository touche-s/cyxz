# 限流与压测验证报告

> 验证日期：2026-08-14
> 验证环境：本地 Docker 单节点部署
> 被测链路：Locust → 网关（8080）→ cyxz-post
> 关联文档：[压测报告](./压测报告.md)、[压测优化分析报告](./压测优化分析报告.md)

## 一、背景与目标

上一轮压测（[压测报告](./压测报告.md)）定位到 5000 并发下后端被「打爆」——失败率 31%，大量请求超时，根因是连接池耗尽且**缺少流量入口保护**。

本轮工作目标：

1. 在网关注入限流，让超额流量在入口被拦截，避免后端被压垮。
2. 修复压测过程中暴露的若干启动/配置/构建缺陷。
3. 用 200 / 5000 两档并发验证限流效果。

---

## 二、限流方案

采用 Spring Cloud Gateway 内置的 `RequestRateLimiter` + `RedisRateLimiter`（令牌桶），复用已有 Redis，不引入额外客户端依赖。

### 2.1 实现位置

| 文件 | 作用 |
|---|---|
| `cyxz-gateway/.../config/RateLimitConfig.java` | `ipKeyResolver`（按 IP 维度取 key）+ `RedisRateLimiter` Bean |
| `cyxz-gateway/.../config/RouteConfig.java` | 给 `post` 路由挂 `requestRateLimiter` 过滤器 |

### 2.2 限流参数

| 参数 | 值 | 含义 |
|---|---|---|
| `replenish-rate` | 200 | 每秒补充 200 个令牌 |
| `burst-capacity` | 400 | 桶容量 400，允许瞬时突发 |

参数可通过配置项 `app.rate-limit.replenish-rate` / `app.rate-limit.burst-capacity` 调整。

### 2.3 限流语义（令牌桶）

- 桶容量 400，每秒补 200 个令牌。
- 请求到达：有令牌 → 放行并扣 1 个；无令牌 → **立即返回 429**，不排队、不阻塞。
- 这是「超限直接拒绝」，而非「排队慢慢放行」。

## 三、压测前修复的问题

压测准备阶段发现并修复了 4 个缺陷，均为代码实锤：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 网关启动崩溃 | 网关（响应式）扫描 `com.cyxz.common` 时硬实例化 Servlet 专用组件 | `GlobalExceptionHandler`、`PreventRepeatAspect` 加 `@ConditionalOnWebApplication(SERVLET)` |
| 2 | 点赞/收藏尾延迟高 | `rabbitmq` 配置误写在 `spring.data` 下，导致连到 `localhost:5672` | post/user/circle/governance/audit 5 个 YAML 缩进修正 |
| 3 | post 缺 aspectj | `PreventRepeatAspect` 依赖 aspectj，但 common 中为 `provided` 不传递 | post pom 补 `spring-boot-starter-aop` |
| 4 | post 无法重编译 | `EsFullSyncRunner` 引用了 search 完整服务的 `PostSearchRepository` | 移除该直接依赖，ES 同步仍走 MQ |

## 五、压测结果

### 5.1 200 并发（修复后复测）

| 指标 | 数值 |
|---|---|
| 请求总数 | 5166 |
| 失败率 | **0%** |
| 聚合中位数 / 平均 | 13ms / 257ms |

各接口明细：

| 接口 | 请求数 | 中位数 | P95 | 最大 |
|---|---|---|---|---|
| 读-帖子列表 | 2093 | 7ms | 29ms | 203ms |
| 读-帖子详情 | 1220 | 12ms | 3000ms | 6040ms |
| 写-点赞 | 432 | 43ms | 3500ms | 6510ms |
| 写-收藏 | 410 | 39ms | 3000ms | 6159ms |
| 写-取消点赞 | 408 | 28ms | 3000ms | 5833ms |
| 写-取消收藏 | 403 | 30ms | 3000ms | 5717ms |

**解读：** 列表接口 P95 从修复前的 6.4s 降到 29ms，说明 rabbitmq 配置修复显著降低了系统整体抖动。详情与写接口仍有 P90 2-3s 尾延迟，是 HikariCP 连接池（20 连接 + 3s 超时）在高并发下的排队，属已知瓶颈（见[压测优化分析报告](./压测优化分析报告.md)）。

### 5.2 5000 并发（限流验证）

| 指标 | 数值 |
|---|---|
| 请求总数 | 17711 |
| 失败率 | 75.53% |
| 总吞吐 | 265 req/s（含失败） |
| 成功吞吐 | 约 65 req/s |
| 聚合中位数 | 140ms |

失败构成（关键）：

| 失败类型 | 数量 | 占比 | 含义 |
|---|---|---|---|
| ConnectionAborted（10053） | ~10300 | ~77% | 客户端主动断连，请求未到达网关 |
| 429 Too Many Requests | ~2100 | ~16% | 限流器正确拒绝超额流量 |
| ConnectionReset（10054） | ~323 | ~2% | 连接被重置 |

**后端状态：** 网关与 post 服务全程存活，未崩溃（上一轮 5000 并发会把后端打爆）。

## 六、结论

### 6.1 限流方向正确

- 限流生效：约 2100 个请求被 429 拦截，后端从「打爆崩溃」变为「存活 + 优雅降级」。
- 相比上一轮（5000 并发 31% 失败 + 后端崩溃），本次后端全程健康。

### 6.2 本次 5000 压测的局限

本次 5000 并发测试**未能干净地测出限流器真实能力**，原因：

1. 失败构成中 77% 是 Locust 客户端主动断连（单机 5000 并发 + 500/s 高速爬升，客户端先扛不住），请求未到达网关。
2. 成功吞吐仅约 65 req/s，远低于限流阈值 200 QPS，说明后端未被真正压满。
3. 真正被限流 429 的仅约 2100 个，占比不高。

即：**「名义并发 5000」很高，但「有效并发」很低**，测试被单机客户端瓶颈拖累。

## 七、遗留问题与后续建议

| 项 | 说明 | 建议 |
|---|---|---|
| 其他服务缺 AOP | user/comment/circle/message/search/upload/auth 下次重建会踩 `PreventRepeatAspect` 的 aspectj 坑 | 补 `spring-boot-starter-aop` |
| 限流维度 | 当前按 IP，本地压测所有流量共用一个桶，不真实 | 改为按 `X-User-Id` 维度，每用户独立桶 |
| 客户端瓶颈 | 单机 Locust 5000 并发产生大量断连 | 用 Locust master + 多 worker 分布式压测 |
| 限流参数 | 200/400 是保守默认值，未验证是否误伤正常流量 | 结合梯度压测（50→5000）找合理阈值 |
