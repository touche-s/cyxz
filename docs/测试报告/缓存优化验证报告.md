# 缓存优化验证报告

> 验证日期：2026-08-15
> 验证环境：本地 Docker 单节点部署
> 被测链路：k6 → 网关（8080）→ cyxz-post
> 关联文档：[压测报告](./压测报告.md)、[压测优化分析报告](./压测优化分析报告.md)、[限流与压测验证报告](./限流与压测验证报告.md)

---

## 一、背景与目标

限流保护落地后，读路径仍存在冗余跨服务调用：列表/详情每次请求都通过 Feign 拉取圈子名、板块名、用户资料，高并发下拖慢响应、放大失败率。

本轮目标：

1. 圈子名 / 板块名 / 用户资料落地「查一次存」Redis 缓存，减少读路径 Feign 调用。
2. 用 k6 以 2500 VU 重测，对比缓存前后的失败率与延迟。

---

## 二、缓存方案

### 2.1 圈子名 / 板块名缓存

| 项 | 说明 |
|---|---|
| 常量 | `CIRCLE_NAME_PREFIX`、`SECTION_NAME_PREFIX`（TTL 60 分钟） |
| 实现 | `PostQueryService.extractCircleNameMap / extractSectionNameMap`：查一次存，未命中再 Feign 回填 |

### 2.2 用户资料缓存（本轮新增）

| 项 | 说明 |
|---|---|
| 常量 | `USER_PROFILE_PREFIX`（TTL 60 分钟） |
| 实现 | `PostQueryService.getUserProfileMapWithCache`：`multiGet` 批量读 Redis，未命中再 Feign 回填 |
| 替换点 | 详情、按用户列表、列表批量填充三处 `batchGetUserProfiles` 调用 |

读路径每请求少一次 `batchGetUserProfiles` Feign 调用（命中后 0 次 Feign）。

## 四、压测结果

### 4.1 失败率演进（同一压测模型）

| 阶段 | 失败率 | 备注 |
|---|---|---|
| 无缓存 | 9.92% | k6 2500 VU |
| 圈子名缓存 | 0.52% | k6 2500 VU |
| **圈子名 + 用户资料缓存** | **0.00%** | 首轮 17024 请求 0 失败，历史最佳 |

> 参照：[压测报告](./压测报告.md) 中 Locust 2500 并发基线失败率为 7%。

### 4.2 延迟

首轮（缓存填充后）整体：avg 8.9s，P95 28.09s，P99 29.15s。延迟仍受 2500 VU 打 200 Tomcat 线程的排队影响，但无超时失败。

### 4.3 二轮触发 429 限流

连续压测第二轮，缓存已热、请求加速（RPS 184 → 293），触发网关单 IP 限流：

| 指标 | 数值 |
|---|---|
| 失败率 | 13.3%（3911 / 29396） |
| 失败构成 | **全部为 429** |

限流按客户端 IP 维度（阈值 500 QPS / 600 突发），压测全从 `127.0.0.1` 发出，2500 VU 共享同一令牌桶，瞬时突发顶爆限流墙。

---

## 五、结论

1. 用户资料缓存落地，读路径少一次 Feign，失败率降至历史最低 **0.00%**。
2. 缓存让后端吞吐提升，压力被顶到网关限流层（429 兜底），后端未被穿透。
3. 瓶颈已从 **HikariCP 连接池** 转移到 **网关限流（500 QPS/单 IP）+ Tomcat 线程池（200）**。

### 后续建议

| 项 | 说明 |
|---|---|
| 测真实上限 | 临时调高/关闭网关限流，或 k6 多源 IP，跑梯度压测找缓存优化后的真实 QPS 拐点 |
| 限流维度 | 按 IP 维度对本地压测不真实，可改为按 `X-User-Id` 每用户独立桶 |
| 多节点 | 单机 Tomcat 200 线程是硬约束，水平扩展可线性提升吞吐 |
