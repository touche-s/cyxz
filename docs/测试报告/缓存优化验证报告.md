# 缓存优化验证报告

> 验证日期：2026-08-15
> 验证环境：本地 Docker 单节点部署
> 被测链路：k6 → 网关（8080）→ cyxz-post
> 关联文档：[压测报告](./压测报告.md)、[压测优化分析报告](./压测优化分析报告.md)、[限流与压测验证报告](./限流与压测验证报告.md)

---

## 一、背景与目标

限流保护落地后，读路径仍存在冗余跨服务调用：列表/详情每次请求都通过 Feign 拉取圈子名、板块名、用户资料，高并发下拖慢响应、放大失败率。

本轮目标：

1. 圈子名 / 板块名 / 用户资料落地「查一次存」Redis 缓存，减少读路径 Feign 调用。
2. 用 k6 以 2500 VU 重测，对比缓存前后的失败率与延迟。

---

## 二、缓存方案

### 2.1 圈子名 / 板块名缓存

| 项 | 说明 |
|---|---|
| 常量 | `CIRCLE_NAME_PREFIX`、`SECTION_NAME_PREFIX`（TTL 60 分钟） |
| 实现 | `PostQueryService.extractCircleNameMap / extractSectionNameMap`：查一次存，未命中再 Feign 回填 |

### 2.2 用户资料缓存（本轮新增）

| 项 | 说明 |
|---|---|
| 常量 | `USER_PROFILE_PREFIX`（TTL 60 分钟） |
| 实现 | `PostQueryService.getUserProfileMapWithCache`：`multiGet` 批量读 Redis，未命中再 Feign 回填 |
| 替换点 | 详情、按用户列表、列表批量填充三处 `batchGetUserProfiles` 调用 |

读路径每请求少一次 `batchGetUserProfiles` Feign 调用（命中后 0 次 Feign）。

### 2.3 点赞/收藏关系状态缓存（2026-08-16 补充）

| 项 | 说明 |
|---|---|
| 常量 | `USER_LIKED_POSTS`、`USER_COLLECTED_POSTS`、`RELATION_CACHE_TTL_DAYS = 30`、空占位哨兵 `__empty__` |
| 结构 | `user:liked:posts:{userId}` → Set&lt;postId&gt;（同理 `user:collected:posts:{userId}`） |
| 读路径 | `getLikedPostIds/getCollectedPostIds`：读 Redis Set（懒加载，miss 查 DB 回填 + 空集合占位防穿透） |
| 写路径 | 点赞/收藏在 DB 事务提交后（afterCommit）SADD/SREM + `EXPIRE` 续期 |

列表/详情缓存命中后的互动状态补填，从「2 次查关系表」降为「读 Redis Set」，0 次 DB。

## 四、压测结果

### 4.1 失败率演进（同一压测模型）

| 阶段 | 失败率 | 备注 |
|---|---|---|
| 无缓存 | 9.92% | k6 2500 VU |
| 圈子名缓存 | 0.52% | k6 2500 VU |
| **圈子名 + 用户资料缓存** | **0.00%** | 首轮 17024 请求 0 失败，历史最佳 |

> 参照：[压测报告](./压测报告.md) 中 Locust 2500 并发基线失败率为 7%。

### 4.2 延迟

首轮（缓存填充后）整体：avg 8.9s，P95 28.09s，P99 29.15s。延迟仍受 2500 VU 打 200 Tomcat 线程的排队影响，但无超时失败。

### 4.3 二轮触发 429 限流

连续压测第二轮，缓存已热、请求加速（RPS 184 → 293），触发网关单 IP 限流：

| 指标 | 数值 |
|---|---|
| 失败率 | 13.3%（3911 / 29396） |
| 失败构成 | **全部为 429** |

限流按客户端 IP 维度（阈值 500 QPS / 600 突发），压测全从 `127.0.0.1` 发出，2500 VU 共享同一令牌桶，瞬时突发顶爆限流墙。

### 4.4 调高限流后的梯度压测（真实上限，2026-08-16）

临时将网关限流调至 5000 QPS / 6000 突发，揭开限流盖子，用 `--vus` 跑梯度，找缓存优化后的真实吞吐拐点：

| VU | 失败率 | RPS | P95 | 中位数 |
|---:|---:|---:|---:|---:|
| 500 | 0.29% | 165 | 3.49s | 18.65ms |
| 1000 | 0.63% | 274 | 5.56s | 486ms |
| 2500 | 2.79% | 368 | 10.54s | 3.66s |
| 5000 | 2.25% | 377 | 19.21s | 8.16s |
| 2500（热缓存） | 1.66% | 526 | — | — |

**失败构成分析：** 失败全部为 `dial: connection refused`（TCP 连接拒绝），不是 429、不是业务超时、不是 DB 错误。

**关键发现：** `connection refused` 发生在 `k6 → 网关` 的连接建立阶段，即网关的 Netty accept 队列 + 操作系统 socket 参数（`somaxconn` / 文件描述符），而非 post 的 Tomcat。压测链路为 `k6 → 网关(Netty, 8080) → post(Tomcat, 9003)`，post 在网关之后，调 post 的 `maxThreads` / `acceptCount` 不影响网关接连接——实测调 post Tomcat 线程 200→400 后失败类型不变，印证该结论。

## 五、结论

1. 圈名 / 板块名 / 用户资料缓存落地，读路径少 Feign，失败率降至历史最低 **0.00%**。
2. 点赞 / 收藏关系状态缓存落地，互动状态补填从「2 次查关系表」降为「读 Redis Set」。
3. 缓存让后端吞吐提升，压力一路后移：HikariCP → 网关限流 → 连接层。
4. **真实吞吐上限 ≈ 370～530 RPS**（冷缓存 368 / 热缓存 526），失败为 `connection refused`，瓶颈在网关 Netty 连接层 + 操作系统 socket 参数。

### 瓶颈演进

| 阶段 | 瓶颈 | 表现 |
|---|---|---|
| 无缓存 | HikariCP 连接池（DB） | 超时失败 |
| 缓存优化后 | 网关限流 500 QPS | 429 |
| 揭开限流后 | 网关 Netty 连接层 | connection refused |

### 后续建议

| 项 | 说明 |
|---|---|
| 多节点 + 负载均衡 | 单机连接层是硬约束，水平扩展可线性提升吞吐（突破上限的正路） |
| 网关连接层调优 | 调 Netty accept 队列 + 操作系统 `somaxconn` / 文件描述符，收益递减 |
| 限流维度 | 按 IP 维度对本地压测不真实，可改为按 `X-User-Id` 每用户独立桶 |
