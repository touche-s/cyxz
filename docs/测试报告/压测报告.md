## 三、测试场景

### 3.1 被测接口

| 接口 | 方法 | 路径 | 类型 | 认证 | 权重 |
|------|------|------|------|:---:|:---:|
| 帖子列表 | GET | `/api/post/list?sortBy=latest&page=1&size=10` | 读 | 白名单 | 5 |
| 帖子详情 | GET | `/api/post/{id}` | 读 | JWT | 3 |
| 点赞帖子 | PUT | `/api/post/{id}/like` | 高频写 | JWT | 1 |
| 取消点赞 | DELETE | `/api/post/{id}/like` | 高频写 | JWT | 1 |
| 收藏帖子 | PUT | `/api/post/{id}/collect` | 高频写 | JWT | 1 |
| 取消收藏 | DELETE | `/api/post/{id}/collect` | 高频写 | JWT | 1 |

### 3.2 场景设计

- **用户行为模型：** 模拟真实社区用户，浏览列表 → 看详情 → 点赞/收藏，读操作权重 8，写操作权重 4
- **思考时间：** 每个请求间随机等待 1-3 秒（`wait_time = between(1, 3)`），模拟真实用户阅读间隔
- **Token 分配：** 每个虚拟用户分配独立 JWT（同账号多 Token，JWT 各不相同），模拟多用户并发
- **防重规避：** 点赞与取消点赞（PUT/DELETE）交替执行，URI 不同不触发 `@PreventRepeat(2s)` 拦截

### 3.3 涉及的技术机制

压测过程中以下自研机制同时生效，验证其在高并发下的稳定性：

| 机制 | 说明 |
|------|------|
| `@PreventRepeat` + Lua | AOP + Redis Lua 原子脚本，2 秒内同用户同操作防重 |
| Redis 计数刷库 | 点赞/收藏计数先写 Redis，异步刷 DB，降低写压力 |
| AC 自动机敏感词检测 | 发帖/评论内容过滤（本次压测未触发，因无发帖场景） |
| JWT 网关认证 | Gateway 解析 JWT 并传递信任头到下游服务 |
| HikariCP 连接池 | MySQL 连接池（默认 maxPoolSize=10） |
| Tomcat 线程池 | 默认 maxThreads=200 |

## 四、测试步骤

```bash
# 1. 启动服务（docker-compose 一键拉起）
cd docker
docker compose up -d

# 2. 等待基础服务健康（约 3 分钟）
docker ps  # 确认 mysql/redis/rabbitmq/nacos/elasticsearch 均 healthy

# 3. 安装 Python 依赖
pip install -r scripts/benchmark/requirements.txt

# 4. 批量生成 Token（绕过图形验证码）
cd scripts/benchmark
python gen_tokens.py --count 50 --accounts "你的账号:密码" --gateway-url http://localhost:8080
# 输出：tokens.txt（50 个 JWT）

# 5. 启动 Locust Web UI
python -m locust -f locustfile.py --host=http://localhost:8080

# 6. 浏览器打开 http://localhost:8089 配置并发数开始压测
```

**梯度压测策略：** 从 50 并发开始，逐步加压至 200 → 1000 → 2500 → 5000 → 10000，观察 RPS、失败率、响应时间的变化，定位系统拐点。

## 七、瓶颈分析

### 7.1 瓶颈定位

通过对比 1000 并发（0% 失败）和 2500 并发（7% 失败）的数据，发现：

| 现象 | 分析 |
|------|------|
| 中位数从 19ms 暴涨到 1500ms | 请求在连接池队列中等待，非业务逻辑变慢 |
| 失败请求均为超时（非业务异常） | 连接获取超时，非 `@PreventRepeat` 拦截 |
| RPS 仍在上升（472→613） | 系统仍在处理更多请求，但已接近上限 |
| 10000 并发时 RPS 反降 | 连接被直接拒绝，来不及处理 |

**结论：瓶颈在连接资源（HikariCP + Tomcat 线程池），而非业务逻辑或数据库查询。**

### 7.2 当前默认配置

| 组件 | 参数 | 默认值 |
|------|------|:---:|
| HikariCP | maximumPoolSize | 10 |
| Tomcat | maxThreads | 200 |
| Tomcat | acceptCount | 100 |
| Redis Lettuce | 连接池 | 默认动态 |

### 7.3 优化建议（生产环境）

| 优化项 | 预期效果 |
|--------|----------|
| HikariCP maxPoolSize 调至 20-30 | 提升数据库并发处理能力 |
| Tomcat maxThreads 调至 400 | 提升请求接收能力 |
| 前置 Nginx 限流（limit_req） | 超过承载能力时优雅降级，而非超时 |
| Sentinel 接口限流 | 按接口维度精确控制 QPS 上限 |
| 多节点部署 + 负载均衡 | 水平扩展，线性提升吞吐 |
| Redis 连接池调优 | 提升 `@PreventRepeat` 和计数刷库的并发能力 |

## 八、结论

### 8.1 系统安全承载能力

| 指标 | 数值 |
|------|:---:|
| **零失败最大并发** | 1,000 |
| **零失败最大吞吐** | 472 QPS |
| **极限承载（允许少量失败）** | 2,500 并发 / 613 QPS / 7% 失败 |
| **最佳性能点** | 200 并发 / 100 QPS / 9ms 中位数 |

### 8.2 技术机制验证结果

| 机制 | 压测验证 |
|------|----------|
| `@PreventRepeat` + Lua 防重 | ✅ 全程 0 业务失败，防重拦截未误杀正常请求 |
| Redis 计数刷库 | ✅ 高频写操作中位数 7-22ms，未拖慢响应 |
| JWT 网关认证 | ✅ 1000 并发下认证无延迟、无失败 |
| AC 自动机敏感词 | ⚪ 本次未触发（无发帖场景），已由单元测试覆盖 |

### 8.3 简历参考写法

> **接口压测与性能验证：** 使用 Locust 对核心接口（帖子列表/详情/点赞/收藏）进行梯度压测，从 50 到 10000 并发逐步加压。系统在 1000 并发下吞吐达 **472 QPS**，零失败，读接口中位数 17-21ms，写接口中位数 17-22ms；极限压测（5000 并发）定位瓶颈为 HikariCP 连接池耗尽（非业务逻辑），为后续连接池调优和限流策略提供数据支撑。验证了 `@PreventRepeat` + Lua 防重、Redis 计数刷库、JWT 网关认证等自研机制在高并发下的稳定性。
