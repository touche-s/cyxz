# 消息通知与关注动态方案

> 消息系统是次元小站从"功能散点"走向"互动闭环"的关键一环。本文档分已实现和规划两部分，已实现内容均基于代码核对。

## 设计定位

社区产品的核心是"发完之后有人看、有人互动、我能收到反馈"。本期目标是在已有的发帖、评论、点赞、收藏、关注之上，补齐 **消息通知 + 关注动态 + 私信** 三条反馈链路，让用户感知到"社区是活的"。

设计原则：

1. **先做结果正确，再做实时性增强** —— 通知必落库，推送是增强
2. **业务服务与消息服务完全解耦** —— 走 MQ 异步，业务不依赖消息服务可用性
3. **幂等优先** —— 重复点赞/收藏/关注不产生重复通知
4. **不做过度设计** —— 单实例 WebSocket、本地内存会话表，先跑通再演进

## 一、已实现

> 基于 `cyxz-message` / `cyxz-message-api` / `cyxz-post` / `cyxz-comment` / `cyxz-user` 模块代码核对。

### 1. 通知数据模型

`notification` 表核心字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 |
| `receiver_id` | bigint | 接收人 |
| `sender_id` | bigint | 触发人（系统通知为 0） |
| `type` | varchar(32) | 通知类型枚举 |
| `target_id` | bigint | 目标对象 ID（null 用 0 占位保证唯一索引生效） |
| `target_type` | varchar(32) | post / comment / user |
| `related_id` | bigint | 关联对象 ID（如评论 ID） |
| `content` | varchar(255) | 文案摘要（超 200 字截断） |
| `is_read` | tinyint | 0 未读 / 1 已读 |

唯一索引 `(receiver_id, type, sender_id, target_id)` 用于幂等去重，重复事件由 `DuplicateKeyException` 静默吞掉。

### 2. 通知类型

`NotificationType` 枚举共 7 种，覆盖社区互动 + 审核结果：

| 类型 | 动作文案 | 触发服务 |
|---|---|---|
| `POST_LIKED` | 赞了你的帖子 | `cyxz-post` |
| `POST_COMMENTED` | 评论了你的帖子 | `cyxz-comment` |
| `COMMENT_REPLIED` | 回复了你的评论 | `cyxz-comment` |
| `POST_COLLECTED` | 收藏了你的帖子 | `cyxz-post` |
| `USER_FOLLOWED` | 关注了你 | `cyxz-user` |
| `POST_APPROVED` | 你的帖子审核通过 | `cyxz-post`（系统通知 senderId=0） |
| `POST_REJECTED` | 你的帖子未通过审核 | `cyxz-post`（系统通知 senderId=0） |

每个类型附带 `frontType` 字段（like/comment/reply/collect/follow/system），供前端归类筛选。

### 3. 异步事件链路（MQ 解耦）

业务服务 → RabbitMQ → `cyxz-message` 消费落库 → WebSocket 推送。

```
用户点赞/评论/关注
   ↓ rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, NotificationEvent)
cyxz.notification.exchange (TopicExchange)
   ↓ ROUTING_KEY = notification.create
cyxz.notification.queue (durable, 绑定死信)
   ↓ @RabbitListener(ackMode = MANUAL)
NotificationEventConsumer
   ├─ notificationService.createByEvent(event)  落库
   ├─ pushIfOnline(event)                       WebSocket 推送
   └─ channel.basicAck / basicReject(false)
```

关键设计：

- **业务服务只发 MQ 消息**，不直接调 Feign，业务事务不依赖消息服务
- **手动 ACK**：消费异常 `basicReject(tag, false)` 进入死信队列，避免消息丢失
- **死信队列**：`cyxz.notification.dlx` + `cyxz.notification.dlq`，便于后续人工排查
- **发送失败 try-catch**：业务侧 `catch Exception` 仅打 warn 日志，不影响主流程
- **常量统一管理**：`NotificationConstants` 集中定义 exchange/routingKey/queue/dlx/dlq，避免魔数

### 4. 去重与边界

- **不给自己发通知**：`receiverId == senderId` 直接 return
- **重复事件幂等**：唯一索引 + `DuplicateKeyException` 静默跳过（同一用户对同一帖子重复点赞只产生一条通知）
- **评论回复去重**：`CommentServiceImpl` 分别判断"帖主"和"被回复评论作者"，避免同人收两条通知
- **取消操作不回收历史通知**：符合主流社区习惯
- **字段合法性校验**：`receiverId` 或 `type` 为空时拒绝落库并打 warn

### 5. WebSocket 实时推送

- **端点**：`/ws/message`，由 `WebSocketConfig` 注册
- **鉴权**：`WebSocketHandshakeInterceptor` 从 URL query 参数提取 `token`，`JwtUtil` 校验后写入 `userId` 到 session attributes；失败返回 401
- **会话管理**：`WebSocketSessionManager` 维护 `userId → WebSocketSession` 的 `ConcurrentHashMap`
  - 新连接建立时关闭同用户的旧连接（防多端)
  - `isOnline(userId)` 判断在线，在线才推送
- **心跳保活**：`@Scheduled(fixedRate = 30000)` 每 30 秒向所有连接发 Ping 帧，发送失败清理半开连接
- **推送协议**：`{type: "notification", data: NotificationEvent}` JSON 信封
- **单实例方案**：本地内存 Map，多实例部署需改 Redis pub/sub 广播

### 6. 通知查询与已读

`NotificationController` 提供完整的通知中心 API：

| 接口 | 说明 |
|---|---|
| `GET /message/notifications` | 分页查询通知，支持 `type` 筛选，按时间倒序 |
| `GET /message/unread-count` | 未读数量 |
| `PUT /message/{id}/read` | 标记单条已读 |
| `PUT /message/read-all` | 全部标记已读 |
| `POST /message/internal/notifications` | 内部接口（Feign 兜底，主链路走 MQ） |

查询时批量调用 `UserFeignClient` 补发送人头像和昵称，避免 N+1。

### 7. 关注动态流

`GET /post/following` 实现拉模式时间线：

1. `UserFeignClient.listFollowingUserIds(userId)` 拉取关注用户 ID 列表
2. `PostMapper` 按 `userId IN (...)` 分页查询已发布帖子
3. 复用 `fillPostVOList` 批量补作者信息、圈子名称、板块名称、当前用户点赞收藏状态

不做预计算 Feed 表，适合当前数据量。

### 8. 私信（额外实现）

在原方案之外，已实现基础私信能力：

- `ChatController`：会话列表、历史消息分页、发送消息、标记已读、总未读数
- `ConversationPO` / `PrivateMessagePO`：会话与消息实体
- WebSocket 仅用于服务端推送，客户端发消息走 HTTP `/message/send`
- 会话维度未读计数，标记已读后归零

### 9. message-api 模块

已建立 `cyxz-message-api`，与 `cyxz-user-api` / `cyxz-post-api` 结构一致：

- `constant/NotificationConstants`：MQ 常量
- `enums/NotificationType`：通知类型枚举
- `event/NotificationEvent`：MQ 事件 DTO（Serializable）
- `dto/CreateNotificationRequest`：Feign 创建通知请求
- `feign/MessageFeignClient` + `fallback/MessageFeignClientFallbackFactory`：Feign 客户端及降级
- `vo/NotificationVO` / `ChatMessageVO` / `ConversationVO`：返回视图

包路径已扁平化为 `com.cyxz.message.*`（无 `api/` 中间层），与其他 api 模块保持一致。

## 二、规划

### 1. 未读数缓存

当前 `unreadCount` 直接 `SELECT COUNT(*)`，未来用 Redis 缓存：

- 写通知时 `INCR receiver:{userId}:unread`
- 标记已读时 `DECRBY` 对应数量
- 查询时优先走缓存， miss 再回库

### 2. 多实例 WebSocket

当前单实例内存 Map，多实例部署需：

- Session 信息存 Redis
- 推送时发布到 Redis pub/sub
- 各实例订阅本机在线用户的消息

### 3. 消息聚合

"张三等 17 人赞了你" 这类聚合通知：

- 新增 `notification_aggregate` 表，按 `(receiver_id, type, target_id, date)` 聚合
- 短时间内同类通知合并，仅保留最新 sender 列表

### 4. 已读回执多端同步

当前标记已读只更新本地库，多端登录时其他端不会立即同步：

- WebSocket 推送 `read_sync` 事件
- 其他端收到后本地更新已读状态

### 5. 通知中心增强

- 按类型 tab 筛选（点赞/评论/关注/系统）
- 通知设置开关（用户可关闭某类通知）
- 邮件/浏览器 Push 通知（Web Notification API）

## 三、技术亮点（简历视角）

> 技术亮点总览见 [README](../../README.md#技术亮点)，以下为本模块特有亮点。

1. **幂等设计**：唯一索引 + `DuplicateKeyException` 实现天然幂等，重复点赞/收藏不产生重复通知
2. **可靠投递**：手动 ACK + 死信队列，消费失败不丢消息，便于人工排查
3. **WebSocket 实时推送**：JWT 握手鉴权 + 30 秒心跳保活 + 半开连接清理，单实例方案足够支撑当前规模
4. **N+1 优化**：通知列表批量 Feign 查询用户信息，避免逐条查询
5. **架构演进路径清晰**：从单实例 → Redis 缓存 → 多实例 pub/sub → 消息聚合，每步都有明确升级点
