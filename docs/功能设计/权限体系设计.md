# 权限体系设计（多租户 RBAC + SpringSecurity 方法级授权）

> 本文记录次元小站的权限架构演进方案：从当前「单角色 + @AdminUser 注解」升级为「多租户 RBAC + SpringSecurity 方法级授权」的标准权限模型。
> 参考 GitHub 组织角色、贴吧吧务体系的"平台角色 + 资源域角色"双层设计，支撑站主、平台管理员、圈主、圈子管理员多角色分级管控。
> 定位为规划文档，落地后同步更新。

---

## 一、设计目标

> **核心概念区分**：本体系涉及两个常被混淆的概念，先明确边界：
> - **权限校验（Permission）**：判断"能不能做某操作"，机制是查权限码做准入，方法执行**前**拦截。无论是全局权限还是租户内权限，本质都是准入校验。
> - **数据隔离（Data Isolation）**：过滤"能看到哪些数据行"，机制是 SQL 层自动拼 `WHERE circle_id = ?`，方法正常执行，结果集被过滤。
> - 两者正交：权限管准入，隔离管范围，不可互相替代。

1. **全局功能权限**：基于全局角色（SITE_OWNER/PLATFORM_ADMIN/USER），控制"能不能访问平台级接口"——站主/平台管理员管全平台，普通用户无管理权限。权限码随 JWT 下发，`hasAuthority('user:manage:disable')` 校验。
2. **租户内功能权限**：基于资源域角色（CIRCLE_OWNER/CIRCLE_ADMIN/CIRCLE_MEMBER），控制"能不能在该圈子内做某操作"——圈主和管理员只管自己的圈子。本质仍是准入校验，只是权限来源是 `sys_user_role(circle_id)` 而非 JWT，由 `@circlePerm.hasAuthority('circle:post:review', #circleId)` 实时查库/缓存校验。
3. **数据隔离（远期演进）**：控制"列表查询能返回哪些圈子的数据行"——通过 MyBatis-Plus `TenantLineInnerInterceptor` 在 SQL 层自动拼 `WHERE circle_id = ?`，业务代码无感知。详见第十二节。
4. **方法级授权**：用 SpringSecurity 的 `@PreAuthorize` + SpEL 统一表达权限校验，支持权限码、角色、组合表达式。
5. **前后端双重控制**：后端注解兜底，前端指令控制 UI 显隐。
6. **多租户 RBAC**：全局角色与圈子内角色统一进 RBAC 体系，通过 `circle_id` 维度区分作用域，权限完全动态可配。

## 二、整体架构

```
客户端 ──> Gateway ──> 下游微服务
            │              │
        认证层             授权层
            │              │
     1. 验 JWT             1. HeaderAuthenticationFilter
     2. 剥离伪造头            读 X-User-Id / X-User-Roles / X-User-Permissions
     3. 注入信任头            → 构造 Authentication
            │              2. SecurityContext 填充
     X-User-Id             3. @PreAuthorize SpEL 校验
     X-User-Roles            ├> hasAuthority('xxx')         全局功能权限
     X-User-Permissions      └> @circlePerm.hasAuthority(   圈子数据权限
                                'circle:post:review', #circleId)
```

**分工**：
- **Gateway**：只管认证（JWT 是否有效），不管授权（有没有权限操作）
- **下游微服务**：用 SpringSecurity 做方法级授权
- **多租户 RBAC**：全局角色（SITE_OWNER / PLATFORM_ADMIN / USER）和圈子内角色（CIRCLE_OWNER / CIRCLE_ADMIN / CIRCLE_MEMBER）统一进 `sys_role` + `sys_user_role` 表，通过 `circle_id` 维度区分作用域

## 三、数据库设计

### 3.1 RBAC 表结构（4 张表）

> 建在 `cyxz_auth` 数据库，由 auth 模块管理。

```sql
-- 角色表（加 scope 区分全局/圈子内，built_in 保护内置角色）
CREATE TABLE sys_role (
    id BIGINT PRIMARY KEY COMMENT '雪花算法',
    code VARCHAR(30) NOT NULL UNIQUE COMMENT '角色标识',
    label VARCHAR(20) NOT NULL COMMENT '显示名',
    scope VARCHAR(20) NOT NULL DEFAULT 'GLOBAL' COMMENT 'GLOBAL全局 / CIRCLE圈子内',
    description VARCHAR(100) COMMENT '描述',
    built_in TINYINT NOT NULL DEFAULT 0 COMMENT '1=内置系统角色，不允许删除/改code；0=业务可维护',
    sort INT NOT NULL DEFAULT 0 COMMENT '排序(小在前)',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB COMMENT='角色表';

-- 权限表（统一一套权限码，不区分全局/圈子）
CREATE TABLE sys_permission (
    id BIGINT PRIMARY KEY COMMENT '雪花算法',
    code VARCHAR(60) NOT NULL UNIQUE COMMENT '权限标识 post:review:approve',
    label VARCHAR(50) NOT NULL COMMENT '显示名',
    resource VARCHAR(30) NOT NULL COMMENT '资源 post/user/circle/upload',
    action VARCHAR(30) NOT NULL COMMENT '操作',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB COMMENT='权限表';

-- 角色-权限关联（动态分配，运营后台可配）
CREATE TABLE sys_role_permission (
    role_id BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,
    PRIMARY KEY (role_id, permission_id)
) ENGINE=InnoDB COMMENT='角色权限关联表';

-- 用户-角色关联（加 circle_id 维度，支持多租户）
CREATE TABLE sys_user_role (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    circle_id BIGINT DEFAULT NULL COMMENT 'NULL=全局角色，非NULL=圈子内角色',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id, role_id, circle_id),
    INDEX idx_user_tenant (user_id, circle_id)
) ENGINE=InnoDB COMMENT='用户角色关联表';
```

### 3.6 业务层强制校验（工业规范必做）

数据库约束无法表达"scope=GLOBAL 的角色 circle_id 必须为 NULL"这种逻辑条件，**必须在 Service 层拦截**，否则会产生严重越权漏洞。

#### 1. 角色 scope 强校验

分配用户角色时校验 scope，防止 CIRCLE 角色被分配为全局角色（导致用户全平台所有圈子都是圈主）：

```java
public void assignRole(Long userId, Long roleId, Long circleId) {
    SysRole role = sysRoleMapper.selectById(roleId);
    if (role == null) throw new BusinessException("角色不存在");
    
    // GLOBAL 角色只能分配到全局域（circle_id=NULL）
    if ("GLOBAL".equals(role.getScope()) && circleId != null) {
        throw new BusinessException("全局角色不能分配到圈子");
    }
    // CIRCLE 角色必须指定 circle_id
    if ("CIRCLE".equals(role.getScope()) && circleId == null) {
        throw new BusinessException("圈子角色必须指定 circleId");
    }
    
    sysUserRoleMapper.insertUserRole(userId, roleId, circleId);
    // 清缓存
    evictPermissionCache(userId, circleId);
}
```

#### 2. 内置角色保护

`SITE_OWNER` / `PLATFORM_ADMIN` 等内置角色（`built_in=1`）禁止删除和修改 code：

```java
public void deleteRole(Long roleId) {
    SysRole role = sysRoleMapper.selectById(roleId);
    if (role != null && role.getBuiltIn() == 1) {
        throw new BusinessException("内置角色不允许删除");
    }
    sysRoleMapper.deleteById(roleId);
}
```

#### 3. 站主保护

业务层校验目标用户角色，防止平台管理员操作站主：

```java
public void disableUser(Long targetUserId) {
    if (hasRole(targetUserId, "SITE_OWNER") && !isCurrentUserSiteOwner()) {
        throw new BusinessException(ErrorCode.FORBIDDEN, "不能操作站主账号");
    }
    sysUserMapper.updateStatus(targetUserId, 0);
}
```

#### 4. circleId 合法性校验

`@circlePerm.hasAuthority` 入口校验 circleId 真实存在，防止传不存在的 ID 绕过：

```java
public boolean hasAuthority(String permissionCode, Long circleId) {
    if (circleId == null || !circleMapper.exists(circleId)) return false;
    // ... 后续校验
}
```

#### 5. 圈主转让事务（完整流程）

转让圈主涉及 4 个数据变更，必须事务包裹 + 缓存清理：

```java
@Transactional(rollbackFor = Exception.class)
public void transferOwner(Long circleId, Long newOwnerId) {
    Long oldOwnerId = circleMapper.selectOwnerId(circleId);
    
    // 1. 删除旧圈主的 CIRCLE_OWNER 角色
    sysUserRoleMapper.deleteUserRole(oldOwnerId, CIRCLE_OWNER_ROLE_ID, circleId);
    // 2. 新增新圈主的 CIRCLE_OWNER 角色
    sysUserRoleMapper.insertUserRole(newOwnerId, CIRCLE_OWNER_ROLE_ID, circleId);
    // 3. 更新 circle.owner_id 冗余字段
    circleMapper.updateOwnerId(circleId, newOwnerId);
    
    // 4. 清除两个用户的圈子权限缓存
    redisTemplate.delete("circle:perm:" + oldOwnerId + ":" + circleId);
    redisTemplate.delete("circle:perm:" + newOwnerId + ":" + circleId);
}
```

#### 6. 缓存失效场景（完整清单）

所有涉及权限变更的操作都必须主动清除缓存：

| 操作 | 清除的 Key |
|---|---|
| 授予/撤销用户圈子角色 | `circle:perm:{userId}:{circleId}` |
| 修改角色拥有的权限（sys_role_permission） | 所有持有该角色的用户的 `circle:perm:*` |
| 转让圈主 | 旧圈主 + 新圈主的 `circle:perm:*:{circleId}` |
| 用户退出圈子 | `circle:perm:{userId}:{circleId}` |
| 修改全局角色权限 | 受影响用户需重新登录（JWT 失效） |

> 高危全局操作接口（如禁用用户、删除圈子）业务层应额外再查一次 DB 权限，不单纯依赖 JWT，防止 JWT 失效窗口期被利用。

## 五、核心组件设计

### 5.1 HeaderAuthenticationFilter（common 模块）

读 Gateway 注入的信任头，构造 SpringSecurity 的 Authentication 对象。**必须同时处理角色（ROLE_ 前缀）和权限码（无前缀），否则 `hasAuthority()` 会失效。**

```java
public class HeaderAuthenticationFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String userId = request.getHeader("X-User-Id");
        if (userId != null) {
            List<GrantedAuthority> authorities = new ArrayList<>();
            // 角色：加 ROLE_ 前缀，供 hasRole() 使用
            String roles = request.getHeader("X-User-Roles");  // "SITE_OWNER,USER"
            if (roles != null) {
                Arrays.stream(roles.split(","))
                      .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
                      .forEach(authorities::add);
            }
            // 权限码：无前缀，供 hasAuthority() 使用
            String perms = request.getHeader("X-User-Permissions");
            if (perms != null) {
                Arrays.stream(perms.split(","))
                      .map(SimpleGrantedAuthority::new)
                      .forEach(authorities::add);
            }
            Authentication auth = new UsernamePasswordAuthenticationToken(
                Long.valueOf(userId), null, authorities);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(request, response);
    }
}
```

> **安全约束**：`X-User-Id` / `X-User-Roles` / `X-User-Permissions` 仅允许 Gateway 内部转发注入，业务服务禁止对外暴露。Gateway 入口已无条件剥离客户端传入的这些头，防止绕过网关伪造身份。

### 5.2 BaseSecurityConfig（common 模块基类）

各微服务继承此基类，统一无状态 + 注解鉴权。

```java
public abstract class BaseSecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .formLogin(form -> form.disable())
            .httpBasic(basic -> basic.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .addFilterBefore(new HeaderAuthenticationFilter(),
                UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

### 5.3 权限码注入（必须实现）

> **注意**：`HeaderAuthenticationFilter` 必须同时解析 `X-User-Permissions` 并封装为 `GrantedAuthority`，否则 `hasAuthority('xxx')` 鉴权会直接失效。这不是可选项。

权限码进 SecurityContext 有两种方式：

**方式 A：JWT 里携带全局权限码**（推荐）
- 登录时查全局角色对应的权限列表，写入 JWT 的 `permissions` claim
- Gateway 解析后注入 `X-User-Permissions` 头
- Filter 读头构造 `GrantedAuthority`
- 圈子内权限不进 JWT（每个圈子不同），由 `@circlePerm` 实时查库/缓存

**方式 B：Redis 缓存权限**（可选升级）
- 登录时查权限存 Redis（key=`user:perm:{userId}`）
- Filter 读 Redis 构造权限集合
- 权限变更时主动清缓存

> 推荐 A：减少 Redis 调用，JWT 自带全局权限。圈子内权限可演进到方式 B 的缓存（key=`circle:perm:{userId}:{circleId}`），TTL 10 分钟，角色变更时主动清除。当前规模直接查 DB 足够，见图 5.4 基础版。

### 5.4 CirclePermissionEvaluator（圈子数据权限）

自定义 SpEL Bean，校验当前用户在指定圈子内是否拥有某权限码。基于多租户 RBAC 查询，权限完全动态。

**基础版（直接查 DB，当前推荐）**：

```java
@Component("circlePerm")
public class CirclePermissionEvaluator {

    @Resource
    private SysUserRoleMapper userRoleMapper;
    @Resource
    private SysRolePermissionMapper rolePermissionMapper;
    @Resource
    private CircleMapper circleMapper;  // 校验 circleId 合法性

    public boolean hasAuthority(String permissionCode, Long circleId) {
        Long userId = currentUserId();
        if (userId == null) return false;
        if (isGlobalAdmin()) return true;
        
        // 校验 circleId 真实存在，防止传不存在的 ID 绕过
        if (circleId == null || !circleMapper.exists(circleId)) return false;

        List<Long> roleIds = userRoleMapper.selectCircleRoleIds(userId, circleId);
        if (roleIds.isEmpty()) return false;

        Set<String> permissions = rolePermissionMapper.selectPermissionCodes(roleIds);
        return permissions.contains(permissionCode);
    }

    // currentUserId() / isGlobalAdmin() 同下
}
```

> 两次索引查询（`sys_user_role` + `sys_role_permission`），毫秒级，低并发完全够用。

**Redis 增强版（高并发可选升级）**：

```java
@Component("circlePerm")
public class CirclePermissionEvaluator {

    @Resource
    private SysUserRoleMapper userRoleMapper;
    @Resource
    private SysRolePermissionMapper rolePermissionMapper;
    @Resource
    private StringRedisTemplate redisTemplate;

    public boolean hasAuthority(String permissionCode, Long circleId) {
        Long userId = currentUserId();
        if (userId == null) return false;
        if (isGlobalAdmin()) return true;

        // 先查 Redis
        String cacheKey = "circle:perm:" + userId + ":" + circleId;
        String cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return Arrays.asList(cached.split(",")).contains(permissionCode);
        }

        // 未命中：查 DB 并缓存
        List<Long> roleIds = userRoleMapper.selectCircleRoleIds(userId, circleId);
        if (roleIds.isEmpty()) return false;

        Set<String> permissions = rolePermissionMapper.selectPermissionCodes(roleIds);
        if (permissions.isEmpty()) return false;

        redisTemplate.opsForValue().set(cacheKey, String.join(",", permissions),
                Duration.ofMinutes(10));
        return permissions.contains(permissionCode);
    }

    private Long currentUserId() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        return auth == null ? null : (Long) auth.getPrincipal();
    }

    private boolean isGlobalAdmin() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        return auth != null && auth.getAuthorities().stream().anyMatch(a ->
            a.getAuthority().equals("ROLE_SITE_OWNER") ||
            a.getAuthority().equals("ROLE_PLATFORM_ADMIN"));
    }
}
```

> Redis Key: `circle:perm:{userId}:{circleId}`，Value: 逗号分隔的权限码。懒写 + 变更时删。TTL 10 分钟（±1 分钟随机偏移防雪崩），角色变更时主动 `DELETE`。

### 5.5 认证授权链路规范

**Gateway 职责（只做认证）**：
1. 校验 JWT 签名，判断用户是谁
2. **只提取【全局角色、全局权限】注入 Header**（`X-User-Id` / `X-User-Roles` / `X-User-Permissions`）
3. **完全不查询任何圈子角色**（用户可能加入几十个圈子，JWT/Header 装不下）
4. **强制清除客户端原始传入的 `X-User-*` 请求头**，防止绕过网关伪造身份

**业务服务职责（做授权）**：
1. `HeaderAuthenticationFilter` 读取网关可信头，组装 `Authentication`，里面**只有全局角色和全局权限**
2. `@PreAuthorize` 做两层校验：
   - 第一层：全局功能权限（`hasAuthority` / `hasRole`）
   - 第二层：租户域权限，调用 `@circlePerm.hasPermission(code, #circleId)` 实时查询

> **规范原则**：全局权限和租户权限两套来源，不能混为一谈。全局权限不感知任何 circle_id；租户权限强绑定 circle_id。

### 5.7 完整请求流程

> 本节按"请求生命周期"组织，覆盖登录、接口调用、权限变更、圈主转让、全局权限变更五个核心场景。面试时按此顺序讲解最清晰。

#### 流程 1：用户登录

```
1. 用户提交账号密码 → auth 模块校验身份
2. 查全局角色：SELECT role_id FROM sys_user_role WHERE user_id=? AND circle_id IS NULL
3. 根据全局角色查全局权限码（sys_role_permission + sys_permission）
4. 将 userId + roles + permissions 写入 JWT 的 claim
   ❗ 不查用户加入了哪些圈子、圈子内角色，不写入 JWT
   原因：用户可能几十上百个圈子，token 装不下；且圈子权限动态变化
5. 返回 token 给前端
```

#### 流程 2：接口请求（以审核圈子 3 的帖子为例）

接口签名：
```java
@PreAuthorize("hasAnyRole('SITE_OWNER','PLATFORM_ADMIN') or " +
             "@circlePerm.hasAuthority('circle:post:review', #circleId)")
@PutMapping("/circle/{circleId}/post/{postId}/approve")
public Result<Void> approve(@PathVariable Long circleId, @PathVariable Long postId) { ... }
```

```
1. 客户端发请求，带 JWT

2. Gateway 处理：
   2.1 强制删除客户端自带的 X-User-Id / X-User-Roles / X-User-Permissions（防伪造）
   2.2 校验 JWT 签名，解析出 userId、全局 roles、全局 permissions
   2.3 注入内部可信头，转发给下游微服务

3. 业务微服务接收：
   3.1 HeaderAuthenticationFilter 执行，读可信头组装 Authentication
       → SecurityContext 中只有全局角色和全局权限，圈子权限完全没有
   3.2 进入 @PreAuthorize 的 SpEL 表达式

4. SpEL 短路求值：
   4.1 第一步：hasAnyRole('SITE_OWNER','PLATFORM_ADMIN')
       → 是站主/平台管理员 → true → 直接放行进 Controller
   4.2 不是全局管理员 → 进入第二步

5. 执行 @circlePerm.hasAuthority('circle:post:review', circleId=3)：
   5.1 校验 circleId=3 真实存在（防传不存在的 ID 绕过）
   5.2 查 Redis 缓存 key = circle:perm:{userId}:3
       → 命中：直接判断权限码是否在集合中，返回 true/false
   5.3 未命中：查 DB
       → sys_user_role 查用户在圈子 3 的所有 role_id
       → sys_role_permission + sys_permission 查这些角色的权限码集合
       → 回写 Redis（TTL 10 分钟 ± 1 分钟随机偏移）

6. SpEL 得到最终布尔结果：
   → true：放行执行 Controller 业务逻辑
   → false：抛 AccessDeniedException，返回 403
```

> **重点**：圈子权限不在 SecurityContext 里，是每次方法校验时通过 SpEL 组件实时计算。

#### 流程 3：权限变更（授予圈子管理员）

业务：给用户 A 授予圈子 3 的 CIRCLE_ADMIN 角色。

```
1. Service 层前置校验：
   → CIRCLE_ADMIN 的 scope=CIRCLE，传入的 circleId=3 必须真实存在
   → 校验操作者本人是否有 circle:member:manage 权限（或全局管理员）

2. 事务内执行：
   → INSERT sys_user_role(userA, CIRCLE_ADMIN, circle_id=3)

3. 事务提交后清除 Redis 缓存：
   → DELETE circle:perm:{userA}:3
   → 旧权限缓存作废，下次请求重新加载（不依赖 TTL 过期）
```

> 同理：撤销圈子角色、修改角色拥有的权限（sys_role_permission），都要删除对应缓存 key。

#### 流程 4：圈主转让

业务：把圈子 3 的圈主从用户旧 → 用户新。

```
1. 开启数据库事务：
   1.1 DELETE sys_user_role(oldUserId, CIRCLE_OWNER, circle_id=3)
   1.2 INSERT sys_user_role(newUserId, CIRCLE_OWNER, circle_id=3)
   1.3 UPDATE circle SET owner_id=newUserId WHERE id=3

2. 事务提交成功

3. 清除两个人的缓存：
   → DELETE circle:perm:{oldUserId}:3
   → DELETE circle:perm:{newUserId}:3
```

> **关键约束**：不能只改 `circle.owner_id` 而不动 `sys_user_role`——owner_id 只是业务查询冗余，权限校验以 sys_user_role 为准，两者不一致会导致权限和数据展示矛盾。事务失败全部回滚。

#### 流程 5：全局权限变更（修改平台管理员角色权限）

```
1. 修改 sys_role_permission：给 PLATFORM_ADMIN 角色新增/移除权限

2. 已登录用户：
   → 旧 JWT 仍携带旧权限，需重新登录刷新 token 才生效
   → JWT 一旦签发无法主动失效

3. 规范兜底（高危接口）：
   → 禁用用户、删除圈子等高危操作，业务层额外再查一次 DB 权限
   → 不单纯依赖 JWT，防止失效窗口期被利用
```

> 圈子内权限走 Redis 缓存，变更主动清除秒级生效；全局权限走 JWT，变更需重新登录。两层权限的失效策略不同，这是设计取舍。

## 十、架构核心设计思想

### 多租户 RBAC 双层角色模型

1. **全局角色（sys_role, scope=GLOBAL）**
   - 作用域：全站
   - 绑定主体：用户（`sys_user_role.circle_id = NULL`）
   - 用途：管控平台级管理功能（用户封禁、全局圈子删除等）
   - 成员：SITE_OWNER、PLATFORM_ADMIN、USER

2. **圈子内角色（sys_role, scope=CIRCLE）**
   - 作用域：单个圈子
   - 绑定主体：【用户+圈子】联合关系（`sys_user_role.circle_id = 圈子ID`）
   - 用途：圈子内自治权限（板块管理、圈内帖子审核、任命管理员）
   - 成员：CIRCLE_OWNER、CIRCLE_ADMIN、CIRCLE_MEMBER

### 为什么不把圈子角色做成全局角色

> RBAC 全局角色绑定在用户身上，是用户固有属性；而圈子管理员是依附资源的局部身份，同一用户在 A 圈是圈主、B 圈是普通成员，全局角色无法表达这种差异化。
>
> 通过 `sys_user_role.circle_id` 维度，同一套 RBAC 表既能表达全局角色，也能表达资源域角色，无需额外建表——这是多租户 RBAC 的标准做法。

### 与简化方案的区别

| | 简化方案（圈子域角色不进 RBAC） | 多租户 RBAC（本方案） |
|---|---|---|
| 圈子角色存储 | `circle_member.member_role` 字段 | `sys_user_role(circle_id)` 关联表 |
| 圈子权限来源 | 代码硬编码（@circlePerm.isOwner） | `sys_role_permission` 动态分配 |
| 权限可配置 | 改代码 | 运营后台勾选 |
| 模型完整性 | RBAC 变体 | 标准多租户 RBAC |
| 面试价值 | 中 | 高（GitHub/贴吧同款模型） |

### 与 SaaS 多租户的关系

本方案本质是 SaaS 多租户的**方案 2（共享表 + 隔离列）**：

```
SaaS 多租户：    所有租户共享表，WHERE tenant_id = ?
本系统：         所有圈子共享表，WHERE circle_id = ?
```

区别在于 SaaS 的"租户"是付费企业账号，本系统的"租户"是圈子——数据隔离逻辑完全一致。`sys_user_role.circle_id` 就是租户维度的角色绑定，`@circlePerm.hasAuthority` 是租户维度的权限校验。演进到 Mybatis-Plus `TenantLineInnerInterceptor` 后即为完整的 SaaS 级数据隔离方案。

## 十一、面试要点

1. **为什么 Gateway 管认证、微服务管授权？**
   - Gateway 是统一入口，JWT 校验集中处理避免重复
   - 授权与业务强相关（圈子数据权限），必须在业务服务内判断
   - 分离关注点：认证是"你是谁"，授权是"你能做什么"

2. **功能权限和数据权限的区别？**
   - 功能权限：能不能访问接口（@PreAuthorize hasAuthority）
   - 数据权限：能看到哪些数据（@circlePerm.hasAuthority）
   - 两者正交：先过功能权限再过数据权限，缺一不可

3. **为什么用 SpringSecurity 的 @PreAuthorize 而不是自定义注解？**
   - SpEL 表达力强，支持组合条件
   - 框架成熟，生态完善
   - 面试可讲：SecurityContext + Authentication + GrantedAuthority 体系

4. **多租户 RBAC 是怎么做的？**
   - `sys_user_role` 表加 `circle_id` 维度
   - `circle_id = NULL` 表示全局角色（站主、普通用户）
   - `circle_id = 123` 表示圈子 123 内的角色（圈主、管理员）
   - 同一用户在不同圈子可有不同角色，通过 `circle_id` 隔离
   - 参考 GitHub 组织角色、贴吧吧务体系

5. **权限放在 JWT 有什么优缺点？怎么应对权限实时变更？**
   - 优点：Gateway 直接解析，无需额外 Redis 请求，性能好
   - 缺点：JWT 签发后无法主动失效，权限变更需重新登录生效
   - 优化：全局权限放 JWT，圈子内权限放 Redis 缓存，角色变更时主动清除缓存

6. **圈主权限是怎么控制的？**
   - 圈主在 `sys_user_role` 中绑定 `(user_id, CIRCLE_OWNER, circle_id)`
   - CIRCLE_OWNER 角色通过 `sys_role_permission` 关联了圈子内管理权限码
   - `@circlePerm.hasAuthority('circle:post:review', #circleId)` 查库/缓存校验
   - 运营后台可随时调整 CIRCLE_OWNER 的权限，无需改代码

7. **如何防止角色被分配到错误的作用域？**
   - Service 层强制校验 scope：GLOBAL 角色 circle_id 必须为 NULL，CIRCLE 角色 circle_id 不能为 NULL
   - 数据库约束表达不了这种条件逻辑，必须代码拦截
   - 内置角色（built_in=1）禁止删除和改 code，防止运营误删整个权限体系

8. **圈主转让怎么保证数据一致性？**
   - 事务包裹：删旧圈主角色 + 加新圈主角色 + 更新 circle.owner_id 冗余字段
   - 事务提交后清除两个用户的圈子权限缓存
   - owner_id 只是查询冗余，权限校验以 sys_user_role 为准

9. **JWT 权限失效窗口期怎么应对？**
   - 全局权限放 JWT，变更需重新登录生效
   - 高危接口（禁用用户、删除圈子）业务层额外再查一次 DB 权限，不单纯依赖 JWT
   - 圈子内权限走 Redis 缓存，变更主动清除，秒级生效

### 3. Mybatis-Plus 多租户自动过滤（远期）

当前圈子数据权限通过 `@circlePerm.hasAuthority(code, circleId)` 手动校验。后续可引入 MyBatis-Plus 的 `TenantLineInnerInterceptor`，在 SQL 层自动拼接 `WHERE circle_id = ?`，业务代码不再手写圈子隔离条件。

> 本质是 SaaS 方案 2（共享表 + tenant_id 列自动过滤）。实现仅需一个 `TenantLineInnerInterceptor` Bean（约 30 行），配合 `TenancyContext` ThreadLocal。站主执行全局操作时 `TenancyContext` 为 null，拦截器自动跳过过滤。详见 [MyBatis-Plus 多租户文档](https://baomidou.com/plugins/tenant/)。

```java
// 核心配置（common 模块，~30 行）
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    TenantLineInnerInterceptor tenant = new TenantLineInnerInterceptor();
    tenant.setTenantLineHandler(new TenantLineHandler() {
        @Override
        public Expression getTenantId() {
            Long circleId = TenancyContext.get();
            return circleId != null ? new LongValue(circleId) : null;
        }
        @Override
        public String getTenantIdColumn() { return "circle_id"; }
        @Override
        public boolean ignoreTable(String tableName) {
            return Set.of("sys_user","sys_role","sys_permission",
                "sys_user_role","sys_role_permission","circle").contains(tableName);
        }
    });
    interceptor.addInnerInterceptor(tenant);
    return interceptor;
}
```

> 仅在圈子管理接口数量增多、手动判断成为负担时推进。当前规模用注解 + SpEL 足够，且两者可共存（拦截器和手动条件叠加不影响结果）。
