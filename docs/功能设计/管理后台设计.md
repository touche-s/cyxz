# 管理后台设计

> 最后更新：2026-08-11
> 基于仓库实际代码核对，标注真实实现状态。

## 设计定位

借鉴 OA/ERP 的审批流、审计和权限思路，让后台从"数据查看器"升级为"可运营的管理系统"。

- **流程闭环**：内容发布 → AI 初审 → 人工兜底 → 通知作者，每步可追溯
- **权限最小化**：通过 `@PreAuthorize` + `CirclePermissionEvaluator` 双重校验
- **状态机驱动**：帖子状态流转通过 `ALLOWED_TRANSITIONS` 表强约束，避免非法跃迁
- **AI 优先 + 人工兜底**：常规内容走 AI 自动审核，异常或边界场景转人工

## 一、权限鉴权机制

采用"Gateway 验签透传 + SecurityContext 加载 RBAC + @PreAuthorize 校验"的三段式设计：

```text
客户端 JWT
  → Gateway 验签、剥离外部伪造身份头、注入 X-User-Id
  → HeaderAuthenticationFilter 通过 Redis Cache-Aside / DB 加载权限
  → 构建 SecurityContext（全局权限 + 圈子权限）
  → @PreAuthorize 校验全局权限
  → CirclePermissionEvaluator 校验圈子资源权限
```

**关键设计点：**

- JWT 只保存 userId，不存角色或权限（精简 Token 体积，避免含过期权限）
- Gateway 无条件剥离客户端传入的 `X-User-Id` 头再注入可信值，防止外部伪造
- `/internal/` 路径禁止外部访问，Feign 直调不经网关不受影响
- 权限缓存 TTL 对齐 JWT 剩余时间，避免 Token 过期后旧缓存仍可访问
- 角色/权限/圈子成员变更后，旁路删除 Redis 权限缓存

### 2.2 帖子状态机

`PostStatus` 常量类定义 5 种状态与合法流转表：

```
0 草稿 DRAFT       → 待审核 / 已删除
1 待审核 PENDING   → 已通过 / 拒绝 / 草稿 / 已删除
2 已通过 APPROVED  → 已删除
3 拒绝 REJECTED    → 草稿 / 已删除
4 已删除 DELETED   → 草稿
```

- `ALLOWED_TRANSITIONS` 用 `Map<Integer, Set<Integer>>` 表达流转规则
- `canTransition(from, to)` 校验合法性
- 任意状态均可软删除（`DELETED`）
- 审核操作使用 CAS 更新（`eq(PostPO::getStatus, PENDING)`），防止并发重复审核

### 2.3 帖子审核流程

`PostAdminController` 暴露管理端审核接口，通过 `@PreAuthorize` 鉴权：

| 接口 | 权限码 | 说明 |
|---|---|---|
| `GET /admin/post/review/pending` | `post:review:list` | 待审核帖子分页列表 |
| `PUT /admin/post/review/{postId}/approve` | `post:review:approve` | 审核通过（CAS 更新防并发） |
| `PUT /admin/post/review/{postId}/reject` | `post:review:reject` | 审核拒绝，带原因 |

**通过流程**：

1. 查询帖子 + 状态校验
2. `canTransition` 状态流转合法性校验
3. CAS 原子更新 `status = APPROVED`（防止并发重复）
4. 清缓存 → 增量同步 ES → 发圈子计数事件
5. 发审计事件 + 统计数据事件
6. 通知作者（MQ 异步）

**拒绝流程**：同通过，改为 `status = REJECTED`，记录拒绝原因。

### 2.4 AI 自动审核 + 人工兜底

帖子创建时自动走 AI 审核：

- **AI 通过**：`status = APPROVED`，清缓存，同步 ES，发通知
- **AI 拒绝**：`status = REJECTED`，记录原因
- **AI 异常**：保持 `PENDING`，标记"AI审核服务异常，待人工审核"，等待后台手动处理

AI 审核跑独立线程池 `aiReviewExecutor`（core=2/max=4/CallerRuns），不阻塞业务线程。

### 2.5 举报治理

`cyxz-governance` 作为独立治理中心，只存举报记录 + 发布处置事件，不直接写业务库：

```
用户提交举报 → governance 保存举报记录
  管理员审核通过 → 发布 ContentTakedownEvent
    post/comment 消费 → 处置内容
```

前端 `ReportManagement.vue`：状态筛选、类型筛选、原因搜索、分页、通过/驳回、强制处理意见。

**需审计的操作清单：**

| 操作 | targetType | action |
|---|---|---|
| 审核通过/拒绝帖子 | POST | APPROVE / REJECT |
| 删除帖子 | POST | DELETE |
| 禁用/启用用户 | USER | BAN / UNBAN |
| 分配/变更用户角色 | USER | ASSIGN_ROLE |
| 创建/更新/禁用/删除圈子 | CIRCLE | CREATE / UPDATE / BAN / DELETE |
| 处理举报 | REPORT | APPROVE / REJECT |
| 审核通过/拒绝入圈申请 | APPLICATION | APPROVE / REJECT |
| 审核通过/拒绝建圈申请 | APPLICATION | APPROVE / REJECT |

### 2.6 圈子管理

圈子模块承担圈子、板块、成员、申请的完整领域：

- 创建圈子时自动 `initDefaultSections`：取所有 `ALL` 模板初始化
- 板块采用"模板 + 关联"两层模型，`SectionTemplateController` 管理全站模板
- 建圈申请通过 → 创建 Circle → 指定 owner → 初始化板块（同一模块本地事务）
- 入圈申请通过 → 建立 CircleMember → 更新成员计数 → 刷新权限缓存

### 2.7 数据看板

`cyxz-analytics` 以 CQRS 读模型方式聚合全站统计：

```
业务服务写操作 → 发送 AnalyticsEvent → analytics 消费聚合 → 看板只查 analytics 本地读模型
```

已实现指标：新增用户、新增帖子、审核量、新建圈子、新增入圈、处理举报，支持 7/14/30 天趋势图（ECharts）。

### 2.8 审计日志

`cyxz-audit` 事件驱动审计：

```
管理员敏感操作 → 业务服务发布 AuditEvent → audit 消费并写入审计日志
```

已实现：按操作人/类型/时间检索，按时间范围筛选。

## 四、技术亮点（简历视角）

1. **三段式鉴权架构**：Gateway JWT 验签防伪造 → SecurityContext 加载 RBAC → @PreAuthorize + CirclePermissionEvaluator 双重校验
2. **AI + 人工兜底**：AI 异常时不放行不拒绝，转 `PENDING` 等人工处理（fail-closed 策略）
3. **模板 + 关联两层模型**：板块模板全站统一，圈子按需启用，保证命名一致性
4. **治理中心不写业务库**：governance 只存举报记录 + 发处置事件，post/comment 各自消费完成处置
5. **CQRS 统计读模型**：analytics 独立消费事件聚合，避免管理后台首页 Feign 调用六个服务
6. **审核 CAS 防并发**：approvePost/rejectPost 使用 `LambdaUpdateWrapper.eq(status, PENDING)` 原子更新
