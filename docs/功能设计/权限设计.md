# 权限设计

> 本文合并自原《权限体系设计.md》（规划）与《权限缓存设计.md》（现状），以代码现状为准。
> 规划落地状态：RBAC 表结构 ✅ / @PreAuthorize 方法级授权 ✅ / @circlePerm 圈子数据权限 ✅ / Gateway 注入权限头 ❌（改为服务侧 HeaderAuthenticationFilter 加载，更安全）。

---

## 一、架构原则

| 职责 | 说明 |
|---|---|
| JWT | 仅存 userId / jti / iat / exp，不存角色和权限码 |
| Gateway | 验签 + 注入 X-User-Id + X-Token-Remaining，不查权限 |
| Security Filter | 读 userId → 加载权限 → 构造 SecurityContext |
| Redis | 权限查询结果缓存，TTL 对齐 JWT 过期时间 |
| DB | 权限最终权威来源，Redis 不可用时兜底 |

权限变更实时生效链路：

```text
DB 事务提交 → 删除对应 Redis Key → 下次请求 DB 重建缓存
```

## 二、Redis Key 设计

> 所有 key 统一由 `CacheKeyConstants` 拼接命名空间前缀（`NS` = 系统属性 `redis.namespace`，默认 `cyxz:dev:`），实际 key 形如 `cyxz:dev:auth:global:{userId}`，多环境共用 Redis 时天然隔离。

### 2.1 全局权限缓存

```text
Key:   auth:global:{userId}
Type:  Hash
TTL:   对齐 JWT 过期时间
```

字段：

```text
roles       → SITE_OWNER,PLATFORM_ADMIN
perms       → circle:admin:list,circle:status:update,post:review:list,...
```

写入时机（Cache-Aside 旁观策略）：请求时未命中 → 查 DB → 回写。

删除时机：用户全局角色变更 / 角色权限配置变更（查 DB 找受影响用户逐个删 key）。

### 2.2 圈子权限缓存

```text
Key:   auth:circle:{userId}:{circleId}
Type:  Hash
TTL:   对齐 JWT 过期时间
```

字段：

```text
perms       → circle:section:manage,circle:post:review,circle:post:delete,...
```

写入时机：请求时未命中 → 查 DB → 回写（CirclePermissionEvaluator）。

删除时机：用户圈子角色变更（任命/撤销管理员/踢出成员）/ 角色权限配置变更。

### 2.3 缓存失效矩阵

| 操作 | 失效动作 |
|---|---|
| 用户全局角色变更 | `DEL auth:global:{userId}` |
| 任命圈子管理员 | `DEL auth:circle:{userId}:{circleId}` |
| 撤销圈子管理员 | `DEL auth:circle:{userId}:{circleId}` |
| 踢出成员 | `DEL auth:circle:{userId}:{circleId}` |
| 修改角色权限配置 | 查 DB 找用户 → 逐个 `DEL` |
| 用户登出 | `DEL auth:global:{userId}` |

## 三、Redis 故障降级策略

```
查 Redis
├── 命中 → 使用缓存权限
├── 未命中 → 查 DB → 回写 Redis → 返回
├── Redis 异常 → 查 DB → 返回（不写缓存）
└── Redis + DB 都异常 → 拒绝请求（不放行）
```

**安全底线**：Redis 故障不能导致权限绕过。

## 四、SecurityContext 构造逻辑

```java
// HeaderAuthenticationFilter（cyxz-security 模块）

String userIdHeader = request.getHeader("X-User-Id");
Long userId = Long.valueOf(userIdHeader);

// 加载全局角色和权限（GlobalPermissionProvider 从 Redis/DB）
Set<String> roles = globalPermissionProvider.getRoles(userId);
Set<String> permissions = globalPermissionProvider.getPermissions(userId);

// 构造 GrantedAuthority
List<GrantedAuthority> authorities = new ArrayList<>();
roles.forEach(r -> authorities.add(new SimpleGrantedAuthority("ROLE_" + r)));
permissions.forEach(p -> authorities.add(new SimpleGrantedAuthority(p)));

// 写入 SecurityContext
Authentication auth = new UsernamePasswordAuthenticationToken(userId, null, authorities);
SecurityContextHolder.getContext().setAuthentication(auth);
```

Controller 使用：

```java
@PreAuthorize("hasAuthority('post:admin:list')")              // 功能权限
@PreAuthorize("@circlePerm.hasAuthority('circle:post:review', #circleId)")  // 数据权限
```

> auth 模块 /auth/admin/** 路径额外保留 AdminRoleFilter 做纵深防护（Filter 层先拦非管理员，Controller @PreAuthorize 二次校验），全项目统一 @PreAuthorize 单轨制。

## 五、多租户 RBAC 双层角色模型

### 5.1 模型设计

1. **全局角色（sys_role, scope=GLOBAL）**
   - 作用域：全站
   - 绑定：`sys_user_role.circle_id = NULL`
   - 成员：SITE_OWNER、PLATFORM_ADMIN、USER

2. **圈子内角色（sys_role, scope=CIRCLE）**
   - 作用域：单个圈子
   - 绑定：`sys_user_role.circle_id = 圈子ID`
   - 成员：CIRCLE_OWNER、CIRCLE_ADMIN、CIRCLE_MEMBER

### 5.2 为什么不把圈子角色做成全局角色

> RBAC 全局角色绑定在用户身上，是用户固有属性；而圈子管理员是依附资源的局部身份，同一用户在 A 圈是圈主、B 圈是普通成员，全局角色无法表达这种差异化。
>
> 通过 `sys_user_role.circle_id` 维度，同一套 RBAC 表既能表达全局角色，也能表达资源域角色，无需额外建表——这是多租户 RBAC 的标准做法。

### 5.3 与 SaaS 多租户的关系

本方案本质是 SaaS 多租户的**方案 2（共享表 + 隔离列）**：

```
SaaS 多租户：    所有租户共享表，WHERE tenant_id = ?
本系统：         所有圈子共享表，WHERE circle_id = ?
```

`sys_user_role.circle_id` 就是租户维度的角色绑定，`@circlePerm.hasAuthority` 是租户维度的权限校验。

## 六、面试要点

1. **为什么 Gateway 管认证、微服务管授权？**
   - Gateway 是统一入口，JWT 校验集中处理避免重复
   - 授权与业务强相关（圈子数据权限），必须在业务服务内判断
   - 分离关注点：认证是"你是谁"，授权是"你能做什么"

2. **功能权限和数据权限的区别？**
   - 功能权限：能不能访问接口（@PreAuthorize hasAuthority）
   - 数据权限：能看到哪些数据（@circlePerm.hasAuthority）
   - 两者正交：先过功能权限再过数据权限，缺一不可

3. **为什么用 SpringSecurity 的 @PreAuthorize 而不是自定义注解？**
   - SpEL 表达力强，支持组合条件
   - 框架成熟，生态完善
   - 面试可讲：SecurityContext + Authentication + GrantedAuthority 体系

4. **多租户 RBAC 是怎么做的？**
   - `sys_user_role` 表加 `circle_id` 维度
   - `circle_id = NULL` 表示全局角色（站主、普通用户）
   - `circle_id = 123` 表示圈子 123 内的角色（圈主、管理员）
   - 同一用户在不同圈子可有不同角色，通过 `circle_id` 隔离
   - 参考 GitHub 组织角色、贴吧吧务体系

5. **权限放在 JWT 里还是 Redis 里？为什么？**
   - 本项目 JWT 仅存 userId，权限放 Redis 缓存（Cache-Aside）
   - 优点：权限变更实时生效（删 key 即可），无需用户重新登录
   - 缺点：每次请求需查 Redis（但缓存命中率高，毫秒级）
   - 权衡：权限实时生效 > 省一次 Redis 查询，且高危接口业务层再查 DB 兜底

6. **圈主权限是怎么控制的？**
   - 圈主在 `sys_user_role` 中绑定 `(user_id, CIRCLE_OWNER, circle_id)`
   - CIRCLE_OWNER 角色通过 `sys_role_permission` 关联圈子内管理权限码
   - `@circlePerm.hasAuthority('circle:post:review', #circleId)` 查库/缓存校验
   - 运营后台可随时调整 CIRCLE_OWNER 的权限，无需改代码

7. **如何防止角色被分配到错误的作用域？**
   - Service 层强制校验 scope：GLOBAL 角色 circle_id 必须为 NULL，CIRCLE 角色 circle_id 不能为 NULL
   - 数据库约束表达不了这种条件逻辑，必须代码拦截
   - 内置角色（built_in=1）禁止删除和改 code，防止运营误删整个权限体系

8. **权限缓存怎么保证一致性？**
   - Cache-Aside 旁观策略：写 DB 后删 Redis key，下次请求重建
   - 缓存删除必须在事务提交后（afterCommit），否则可能被旧数据覆盖
   - Redis 故障时降级查 DB，不写缓存；Redis + DB 都故障则拒绝请求

## 七、后续演进项

### 1. Mybatis 拦截器自动数据过滤（远期）

当前 `@circlePerm.hasAuthority(...)` 需接口显式传入 circleId，适合单资源操作。后续列表查询可基于 Mybatis 拦截器自动拼接数据过滤条件。当前规模用注解 + SpEL 足够。

### 2. Mybatis-Plus 多租户自动过滤（远期）

引入 `TenantLineInnerInterceptor`，SQL 层自动拼接 `WHERE circle_id = ?`。本质是 SaaS 方案 2 的完整实现。仅在圈子管理接口数量增多时推进，当前与手动 @circlePerm 可共存。
